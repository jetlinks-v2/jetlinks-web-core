# 应用外壳注册与模块内绑定

状态：已实施（模块内声明绑定，不新增任何管理界面）。消防已迁移为试点，构建期改写已移除。

## 目标

`runtime-ui/modules` 中的业务应用可以携带自己的根布局组件和全局样式，由宿主在 `application` 运行态下挂载，取代当前“构建期改写 `BasicLayoutPage` 导入”和“按菜单 code 猜测应用身份”的做法。应用身份与外壳的绑定关系完全由模块自身在代码里声明，不在后端配置、应用模板或管理页面暴露任何字段。

## 影响范围与 owning module

- owning module：`runtime-ui/jetlinks-web-core`
- 主要入口：`src/layout/BasicLayoutPage.vue`、`src/types/module.ts`、新增 `src/layout/runtime/applicationShell.ts`、新增 `src/layout/shells/ApplicationHostPage.vue`
- 试点应用：`runtime-ui/modules/fire-control-saas-ui`
- 不改：后端实体与接口、`ui/` 运营端、菜单与权限模型、`utils/menu.ts` 中一级路由挂载 `BasicLayoutPage` 的规则

## 明确不做

- 不新增 `configuration.uiModule`、模板字段或应用管理页下拉。
- 不做应用级 Ant Design token / 主题隔离。前提是各应用共用一套 `--jet-theme-*` 与 AntDV 主题；`applyThemeStyle()` 继续写 `document.documentElement`。
- 不引入第二个 Vue App、不接入 micro-app / Module Federation 容器。微前端留作同一契约的第二个适配器，本阶段不实现。
- 不改 `vite.config.ts` 的 `cssCodeSplit`，不迁移 579 处模块静态 `message.*` 与 166 处 `Modal.*`。
- 不动 `store/application.ts` 的远端发现逻辑。

## 契约

`src/types/module.ts` 的 `ModuleDefinition` 新增：

```ts
export interface ApplicationShellContext {
  /** 当前应用运行态 ID（`getApplicationRuntimeEntry().applicationId`）。 */
  applicationId?: string
  /** 菜单是否命中某个标识；别名包含菜单 code、`componentCode`、`routeName`。 */
  hasMenu: (code: string) => boolean
}

export interface ApplicationShellDeclaration {
  /** 应用外壳根组件，内部必须渲染一次页面路由出口。 */
  component: () => Promise<Component>
  /** 命中条件；缺省表示不参与自动匹配，只用于显式调试。 */
  match?: (context: ApplicationShellContext) => boolean
}

// ModuleDefinition
getApplicationShell?: () => ApplicationShellDeclaration | undefined
```

## 解析方式

新增 `src/layout/runtime/applicationShell.ts`，收集方式沿用 `contentPanelOverrides.ts`：首次调用时遍历 `modules()`，把每个模块的 `getApplicationShell()` 放进结果；之后只在实际断言失败时重建。

解析顺序（`ApplicationHostPage` 在 `application` 运行态下求值）：

1. 按 `priority` **降序**遍历已声明外壳的模块，第一个 `match(context)` 返回 `true` 的胜出。降序与现有 `globModules` / `resolveCoreRoutes` 的“后者覆盖前者”语义一致。
2. 两个模块同时命中时，高 `priority` 胜，并对低优先级的模块输出一条 `console.warn`，说明被哪一方接管。
3. 没有命中时返回 `undefined`，回落 `ApplicationLayoutPage`；同时对每个已声明但未命中的模块各告警一次，便于排查菜单改名。

`match` 拿到的 `hasMenu` 直接委托 `menuStore.hasMenu`，其键来自 `getMenuAliasCodes`：菜单 `code`、`meta.componentCode`、`options.componentCode`、`meta.routeName`、`options.routeName`。菜单先于布局路由完成加载（`ensureMenuRoutes` 在 `next()` 之前执行），因此首帧就有值，不会先渲染默认壳再切换。

## 宿主改动

`src/layout/BasicLayoutPage.vue` 只替换 application 分支：

```ts
const layoutComponents = {
  tenant: TenantLayoutPage,
  project: ProjectLayoutPage,
  application: ApplicationHostPage,
}
```

新增 `ApplicationHostPage.vue`：在 `.jl-app-scope` 根节点下渲染命中的外壳，未命中时渲染 `ApplicationLayoutPage`。`tenant` 与 `project` 分支、菜单生成、`contentPanelOverrides` 全部不变。

## 样式约束

因为共用同一套 token，只增加三条硬约束，作为 code review 约定（不做扫描式自动断言：模块里已有 `:global(.xxx)` 这类合法写法，机械扫描会误报）：

- 应用外壳与业务样式的根选择器必须是 `.jl-app-scope` 或其子元素。
- 不得覆盖 `html`、`body`、`:root` 和全局 `.ant-*`。
- 不得通过 `documentElement.style` 写主题变量。

## 消防迁移

`modules/fire-control-saas-ui/runtime/index.ts` 声明外壳，并由 `index.ts` 透出（写法与 `runtime.getCoreRouteOverrides` 一致）：

```ts
getApplicationShell: () => ({
  component: () => import('./layout/FireLayout.vue'),
  match: ({ hasMenu }: ApplicationShellContext) => hasMenu('controlRoom')
    || hasMenu('remoteHome')
    || hasMenu('connectedUserManagement')
    || hasMenu('fireTenantManagement'),
})
```

已完成的配套改动：

- 删除 `modules/fire-control-saas-ui/vite-plugin.js`（构建期把 `BasicLayoutPage` 改写为消防包装层）与 `runtime/layout/ApplicationLayout.vue`。
- 删除只测该插件的 `tests/vite-plugin.test.cjs`，并在 `tests/module-entry.test.cjs` 补 `getApplicationShell` 透出断言，避免以后被误删。
- `useFireApplication` 保留，仍由 `runtime/components/RuntimeFeatures/index.vue` 使用；它与外壳 `match` 使用同一组菜单标识，判定口径一致。

## 风险与待确认

- 绑定键是菜单标识，属于隐式约定。菜单改名会导致外壳回落默认布局，因此 `applicationShell.ts` 对“已声明但未命中”按模块各告警一次（有测试覆盖）。
- 同一应用下若两个模块都希望接管外壳，只能靠 `priority` 胜出，需要在 code review 时显式确认。
- 以后接远程应用时，远端模块同样导出 `getApplicationShell()` 即可复用，无需改宿主；但模块构建产物必须可被 `store/application.ts` 按 `<path>/assets/remoteEntry.js` 加载，这与 `--module-name` / `--modules=` 参数分歧和 `VITE_MICRO_APP` 生产开关同属独立部署阶段的前置项，不在本阶段处理。
