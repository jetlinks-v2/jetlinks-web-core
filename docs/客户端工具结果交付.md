# 客户端工具结果交付

## 当前结论

客户端工具的大结果和 renderer-ready 结果统一经过 `jetlinks-web-core` 的结果交付边界，不再由业务工具各自判断是否上传文件、拼接路径或组装
evidence。交付策略固定为 `session-file → inline → bounded preview`：能安全写入会话文件时交付完整 artifact；文件能力不可用或上传失败时，
在客户端声明的字节上限内交付完整 inline source；完整 source 超限时，仅使用 producer 显式提供的安全 preview。

该契约解决同一 `call.id` 在不同对话或不同轮次中重复使用导致文件覆盖的问题，同时保证关闭文件能力后，模型仍可通过 canonical binding
产出结构化内容块。它是通用客户端工具交付能力，不按工具名、renderer、页面或业务字段特调。

## 影响范围与 owning module

- owning module：`ui/jetlinks-web-core`
- 主要入口：`src/layout/components/AiChat/clientToolResultDelivery.ts`
- 业务接入方：运营端各模块通过通用描述符声明 artifact；业务模块不再直接调用 `sessionFiles.upload`
- 后端配套：`modules/jetlinks-ai-agent` 只负责 runtime source ledger、模型可见投影和 canonical presentation block 物化

## 统一结果契约

现有 `AiClientToolRecordStream` 继续处理记录流。新增中性的 `AiClientToolArtifact`，用于描述一个已经由 producer 准备好的 renderer source：

| 字段 | 语义 |
| --- | --- |
| `source` | 完整、可序列化的 renderer source |
| `mediaType` / `extension` | 媒体类型与安全扩展名 |
| `shape` / `binding` | canonical output binding，不由交付层猜测 |
| `recordCount` | 完整结果数量口径 |
| `maxFileBytes` / `maxInlineBytes` | 当前 artifact 的交付上限 |
| `preview` | producer 显式生成的 renderer-ready 有界预览，可选 |

交付层只处理通用生命周期，不读取领域字段来裁剪 JSON，也不根据 renderer 类型生成 preview。producer 对 source、shape、数量和 preview
正确性负责；交付层对序列化、容量、路径、上传、取消、失败清理和 canonical evidence/output binding 装配负责。

## 交付与生命周期

1. 会话文件可用且完整 source 未超过文件上限时，优先写入 session file，并返回 `fs://` binding。
2. 文件能力关闭、不可用或上传失败时，若完整 source 未超过 inline 上限，则返回 `presentationSource` 与 JSONPath binding。
3. 完整 source 超过 inline 上限时，只能使用 producer 提供的 preview。preview 必须携带 `totalCount`、`displayedCount`、
   `truncated=true`，并生成 partial evidence；没有安全 preview 时仅返回有界 summary、warning 和业务工作区入口。
4. 默认文件名由稳定工具段、可读时间和每次执行生成的 execution UUID 组成。`call.id` 只承担调用关联，不能作为跨 turn 唯一文件名；
   同一执行的分块写入复用同一路径，不同执行永不覆盖。
5. 上传取消或失败时清理本次未完成产物，不删除历史成功产物；错误局部降级，不能让已经成功的业务查询整体失败。

### 幂等补偿与空结果契约

文件删除区分两种语义，不能通过隐藏 `404` 或扩大空 `catch` 混为一谈：

- 用户主动删除保持严格语义，目标不存在时返回 `404`，用于暴露过期状态和错误操作。
- 交付失败或取消后的补偿删除使用 `ignoreMissing=true`；目标已由服务端回滚或其他补偿请求删除时视为成功，但权限、非法路径和存储错误仍正常传播。

客户端交付不再用 `writeAttempted` 猜测文件状态，而是维护 `not-started / unknown / opened / committed / rolled-back`
状态：请求发出但尚未确认时为 `unknown`，分片成功后为 `opened`，交付结果完成装配后才进入 `committed`；仅 `unknown/opened`
允许调用幂等补偿删除。服务端 `FileDeleteOptions` 和 HTTP 删除接口承载统一 `ignoreMissing` 契约，用户文件管理入口继续使用默认严格删除。

记录流成功完成且 `count=0` 时直接返回完整的 empty evidence：不上传空 NDJSON、不产生文件 binding，也不发起补偿删除；该结果不标记为
`fileUnavailable`，避免把“确实没有记录”误报成文件能力故障。

测试目标覆盖：严格删除不存在文件仍为 `404`、幂等删除不存在或重复删除成功、选项跨本地/命令/HTTP 边界保真、上传失败和调用方取消只补偿一次且
携带 `ignoreMissing=true`、零记录无上传/删除请求且 empty evidence 完整。实现不新增按设备、工具、renderer 或页面判断。

## 兼容边界与非目标

- 普通 inline 工具结果和 `AiClientToolRecordStream` 的现有行为不变。
- 已持久化的旧 `fs://` 引用继续只读恢复，不迁移、不双写。
- 设备或其他工具显式声明 `writeToPath` 时，其覆盖/追加语义由业务工具拥有，不被默认 artifact materializer 接管。
- 不新增 renderer 专用分支，不让模型构造文件路径、签名 URL、完整 source 或物理 binding。
- 不改变会话文件权限、业务查询接口、检索算法、页面结构或 `runtime-ui`。

## 验收目标

- 相同 `call.id` 的多轮、多会话执行生成不同路径；同一执行的分块写入复用同一路径。
- 文件开启时返回完整且唯一的 `fs://` binding；文件关闭或上传失败时仍返回可渲染的 inline/partial block。
- partial 结果明确完整数量与展示数量，不能作为完整证据参与后续数据推理。
- 模型可见工具消息不包含完整 renderer JSON、图片签名 URL 或物理文件路径。
- 取消和上传失败不留下半成品，不覆盖历史 artifact，也不改变普通 inline、record stream 与显式 `writeToPath` 行为。
