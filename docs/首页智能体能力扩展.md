# 首页智能体能力扩展计划

## 当前结论

首页智能体不应简单复制设备详情页的专用工具实现，而应复用同一套会话参数契约，将 `iotHome` 作为运行时首页的能力路由入口。首页负责汇聚当前用户可见菜单、可用功能和 provider 主动注册的客户端工具；具体业务模块通过 provider 注册自己的能力说明和工具。

## 影响范围

- owning module：`runtime-ui/jetlinks-web-core`
  - 新增首页智能体能力注册与聚合运行时。
  - 复用 `layout/components/AiChat/clientTools.ts` 的工具描述、确认与结果裁剪能力。
- 接入入口：`runtime-ui/jetlinks-web-core/src/layout/BasicLayoutPage.vue`
  - 全局布局在没有页面专用智能体时恢复 `iotHome` 默认入口，并传入首页上下文、工具、系统提示和链接处理器。
- 参考模块：`runtime-ui/modules/device-manager-ui`
  - 设备“首页”菜单只作为普通菜单能力被首页智能体发现，不再直接挂载 `iotHome`。
- 不调整后端 `jetlinks-ai-agent` 协议，不改 `deviceDetailChat` 设备详情页现有工具实现。

## 最佳实践依据

- MCP 将工具、上下文资源、客户端交互能力分开建模；工具通过描述和 schema 让模型发现和调用，并建议工具暴露、调用过程、人工确认在 UI 中清晰可见。
- MCP 的客户端能力强调由客户端控制用户交互与数据边界，动态补充信息时使用结构化交互，而不是一次性把所有上下文塞进提示词。
- OpenAI Apps SDK 的工具 descriptor 推荐声明结构化输出、只读/破坏性等注解，以及工具调用中的状态元数据；这些原则对应到本项目就是：只读发现工具默认开放，导航/写操作保留明确确认或用户点击。

## 设计入口

### 1. 首页能力 provider

每个模块可注册一个首页能力 provider，包含：

- `id`：provider 唯一标识。
- `getCapabilities(context)`：返回菜单、功能、其他智能体、向导等能力摘要。
- `getClientTools(context)`：返回该模块给首页智能体暴露的客户端工具。
- `getWorkflowGuides(context)`、`getPromptExamples(context)`、`getSystemPromptLines(context)`：可选补充对话引导。

### 2. 首页聚合运行时

首页聚合运行时负责：

- 从菜单 store 读取当前账号可见菜单，压缩为可搜索的能力目录。
- 合并 provider 注册的能力和工具。
- 生成 `clientTools`、`clientToolHandler`、`clientToolsName`、`clientToolsDescription`。
- 生成 `systemPrompt`、`openingStatement`、`promptExamples`、`workflowGuides`。
- 透传前端输入区扩展 `referenceProviders` 与 `composerAddActions`；这些字段只作为 `AgentAccessConversation` props 使用，不进入后端会话 `parameters`。
- 透传 `clientToolsVersion`；页面工具异步注册、刷新或重建后可更新该版本，促使对话会话重新初始化工具契约。
- 文件入口不由页面扩展默认关闭，继续由目标智能体的内置文件工具组决定；只有场景明确不允许文件时才传 `sessionFilesEnabled=false`。
- 提供受控 Markdown 深链，如 `#menu=device%2FInstance`，点击时通过菜单 store 跳转。

### 3. 默认内置工具

- `home_agent_get_context`：查看当前首页视图、路由、菜单数量和能力数量。
- `home_agent_search_capabilities`：按关键词、能力类型搜索菜单/功能/智能体。
- `home_agent_open_menu`：打开已授权菜单，导航前要求用户确认。

### 4. 通用 continuation 交接规范

当首页、列表页或其它通用助手识别到用户需求应由目标页面智能体继续完成时，不应为某个业务场景单独写提示词分支，而应由对应模块的 `homeAgentProvider` 在能力 `metadata.continuation` 中声明通用交接语义：

- `targetName`：面向模型理解的目标助手名称，例如“规则编排助手”“设备详情助手”。
- `promptPolicy`：如何把用户原始目标整理为自然语言 continuation prompt，以及哪些信息可交给目标助手继续确认。
- `blockingFacts`：创建或定位目标对象前必须补齐的最小事实；不包含目标页面稍后可继续追问的完整配置。
- `targetClientId`、`targetMenuCode`、`toolId` 等仅作为 provider 内部执行提示使用，不通过 `home_agent_search_capabilities` 暴露给模型。

公共 system prompt 只在当前上下文存在 continuation 能力时追加通用规则：当前助手保留用户原始目标，补齐创建或定位对象所需的最小事实，优先调用声明工具或入口完成交接；用户可见回复只描述业务结果和下一步，不暴露工具 ID、路由参数、handoff 数据、内部 workflow 或实现细节。

该规范适用于任意需要从通用助手切换到页面专用助手的场景，例如规则编排草稿创建、设备详情诊断、可视化设计或其它配置向导。业务模块只负责声明能力、提供必要工具和保存 handoff；公共层负责能力聚合、提示词约束、搜索结果裁剪和一次性 handoff 消费。

## 实施步骤

1. 在 `jetlinks-web-core` 新增首页能力注册和运行时文件。
2. 在全局布局 `BasicLayoutPage` 接入 `iotHome` 聚合参数；首页能力目录只接收菜单和 provider 声明，不再把 pagePoint 挂载点配置自动转成可发现能力。
3. 为首页智能体添加受控菜单深链处理。
4. 补充国际化文案或沿用现有 AI 对话文案。
5. 运行 `pnpm -C runtime-ui -F jetlinks-web-core build` 验证类型和打包。

## 本次优化计划

- 目标：推荐问题不再使用固定的“设备管理/设备实例”文案，而是按宿主传入、provider 注册和当前可见菜单动态生成。
- 影响范围：`runtime-ui/jetlinks-web-core/src/layout/components/AiChat/homeAgentCapabilities.ts`、`BasicLayoutPage.vue`、`store/ai.ts`、`api/comm.ts`、中英文 i18n。
- 代码落点：`homeAgentCapabilities.ts` 负责能力聚合、工具和提示词；`useGlobalHomeAgent.ts` 负责全局首页智能体参数与 provider 同步；`BasicLayoutPage.vue` 只保留布局级接入。
- 不做：不调整后端协议，不把未部署的本地页面挂载点当成可用智能体，不重构对话 UI。
- 实施：不使用管理端 `pagePoint` 挂载点列表接口，也不在首页初始化时扫描其它 pagePoint 部署；部署查询只用于打开当前 `iotHome` 会话本身。首页能力目录由可见菜单和 provider 声明组成，provider 负责把真实支持的页面功能点、只读工具和提示示例暴露出来。系统提示要求菜单结果使用 `#menu=<menuCode>` 受控链接；推荐问题最多展示 3 条并优先使用注册方提供的示例。
- 风险：模块未注册 provider 时，首页仍可提供菜单发现，但不会宣称存在该页面的专用智能体或工具能力。
- 验证：检查 i18n JSON、运行 `pnpm -C runtime-ui -F jetlinks-web-core build`。

## 当前页能力推荐优化计划

- 目标：首页智能体推荐问题根据当前路由调整；在 `iot/home` 一类首页展示轮换推荐，在业务页面优先展示当前页注册的能力。
- 影响范围：`homeAgentCapabilities.ts`、`useGlobalHomeAgent.ts`、`device-manager-ui/views/device/DashBoard`。
- 不做：不让所有页面自动执行写操作；不从未声明的页面 DOM 中猜测工具参数；不新增后端接口。
- 实施：provider 注册/注销时触发首页智能体参数刷新；设备管理/仪表盘页面注册“分析设备消息聚合”能力和只读客户端工具，工具复用现有 `/dashboard/_multi` 按今日、近 24 小时、近 7 天、近 30 天或自定义时间范围查询消息量、趋势和峰值并返回结构化摘要。
- 动态加载：各业务模块在自身 `register.ts` 中用本模块相对路径扫描能力文件，并通过 `moduleRegistry` 的 `homeAgentProviders` 资源暴露给 core；key 建议使用路由能力编码（如 `device/DashBoard`），value 为 loader。能力文件可通过 `default`、`homeAgentCapabilityProvider` 或 `homeAgentCapabilityProviders` 暴露 provider；不再要求用户先进入对应页面，也不加载页面 SFC 生命周期。
- 路由能力加载：内置 `home_agent_load_route_capabilities` 只导入 provider 文件，不进入页面；全局同步阶段会预加载轻量 provider，确保首页首轮也能看到模块声明能力。provider 仍需自行按 `context.findMenu(...)` 或业务权限判断是否返回工具，避免仅因模块文件存在就暴露未授权能力。
- 首页快捷引导：优先使用 provider 在 `metadata.promptExamples` 中声明的真实业务建议，并按能力交错抽样，避免单个能力占满全部推荐位；未声明推荐语的能力不会只凭能力名称进入首页快捷引导。首页默认优先设备查找、在线状态、告警等高频任务，产品只作为设备筛选或规则配置的解析能力，不作为默认推荐入口；只有没有业务建议时才回退到菜单打开、页面能力列表或功能入口查找等通用兜底。
- 组件主动注册：已进入的页面可调用 `useHomeAgentCapabilityProvider(provider)` 主动注册更贴近当前页面状态的 provider；registry 对同一 provider id 使用栈式覆盖，页面卸载后会恢复模块级 provider，避免把首页可发现能力一并注销。
- 风险：自动把每个页面变成工具能力需要页面声明工具边界，本次先落一个可复用 provider 模板，避免把普通路由误判为可执行工具。
- 验证：检查 i18n JSON、运行 `pnpm -C runtime-ui -F jetlinks-web-core build`。

## 权限与会话体验优化计划

- 目标：确保首页智能体只暴露当前账号真实可访问的页面能力；补充设备列表搜索/选择能力；区分首页通用智能体与设备专用智能体气泡；关闭浮窗时保持会话 WebSocket，气泡展示隐藏期间的新消息数量。
- 影响范围：`runtime-ui/jetlinks-web-core/src/layout/components/AiChat/*`、`runtime-ui/modules/jetlinks-ai-agent-ui/components/AgentAccessConversation`、`runtime-ui/modules/jetlinks-ai-agent-ui/components/AgentConversation`、`runtime-ui/modules/device-manager-ui/views/device/Instance`、`runtime-ui/modules/device-manager-ui/views/device/Instance/Detail`、设备模块中英文 i18n。
- 不做：不新增后端接口；不绕过菜单权限直接跳转隐藏路由；不在首页通用智能体中暴露设备控制、删除、下发等强副作用能力；不把关闭浮窗等同于销毁后端会话。
- 实施：
  1. 在首页能力聚合层增加通用可见性过滤：`menuCode` / `routeName` / `path` 指向菜单的 feature、agent、tool 类能力，默认必须命中 `context.findMenu(...)`；业务 provider 仍可用 `getCapabilities/getClientTools` 做更细粒度条件判断。
  2. 为 `device/Instance` 增加首页能力 provider，提供只读 `device_instance_search` 工具，复用 `/device-instance/_query` 按关键词、产品、状态分页返回候选，并在结果中给出 `#menu=device%2FInstance` 和可继续执行的详情打开工具参数；若需要弹出选择页，优先作为后续可选增强，不在首版新增复杂选择弹窗。
  3. 扩展通用 `AiChat` 气泡参数，支持页面传入 icon / iconBadge / class / tooltip；设备详情页通过 `deviceDetailChat` 参数传专用图标，首页 `iotHome` 保持通用图标。
  4. 保持 `AiChatDrawer` 关闭只隐藏不卸载会话组件；让 `AgentConversation` 在收到 socket 消息、且当前浮窗未打开时向外抛出隐藏消息增量，由 store 记录到气泡 badge；打开浮窗后清零。
- 风险：设备列表 provider 需严格绑定 `device/Instance` 菜单，否则无菜单权限用户仍可能看到工具名；消息计数只能统计前端连接存活期间的新消息，页面销毁或刷新后仍以服务端历史为准；如果 `conversationKey` 因工具契约变化重建组件，WebSocket 仍会按现有规则重连。
- 验证：检查中英文 i18n JSON；验证无 `device/Instance` 菜单时首页能力搜索不返回设备列表/仪表盘能力；在设备详情页关闭浮窗后发送/接收一轮消息，确认 WS 未断开且气泡计数增加，重新打开后计数清零；运行 `pnpm -C runtime-ui -F jetlinks-web-core build`。

## 设备搜索与页面专用助手切换结论

- 设备实例工具注册：`runtime-ui/modules/device-manager-ui/register.ts` 通过 `homeAgentProviders` 暴露 `views/device/Instance/homeAgentProvider.ts`，全局首页智能体通过 `loadHomeAgentCapabilityProviders({ loadAll: true })` 预加载轻量 provider。`device_instance_search` 只在当前账号可见 `device/Instance` 菜单时暴露。
- 搜索契约：`device_instance_search` 按设备列表页已有查询条件类推，支持 `keyword/idOrName/id/name/productId/productName/state/deviceType/describe/classifiedId/accessId/accessProvider/organizationId/organizationName/organizationKeyword`。仅智能体设备搜索工具请求使用 `QueryParamEntity.filter` 表达式，不在前端手工拼 `terms`，也不追加默认 `sorts`，避免影响智能体查询执行计划；设备实例列表页仍保持自身查询和排序逻辑。`keyword` 只生成 `{"id$like":"%关键词%","$or$name$like":"%关键词%"}`；当用户输入无法判断是设备 ID 还是名称时，模型应使用 `keyword` 或 `idOrName` 做 ID/名称模糊搜索；工具内部会把 `like` 条件统一写成 `%关键词%`。数量类问题使用返回的 `total`，可把 `limit` 设小以减少结果体积。
- 关联条件：涉及“某组织/部门下的设备数量或列表”时，模型不应直接猜组织 ID。传入 `organizationName` 或 `organizationKeyword` 后，工具会先查 `/organization/_query/no-paging` 解析组织候选；唯一或精确匹配时再用设备列表同款 `id$dim-assets` 资产维度条件查询设备。多个组织候选时，工具返回 `organizationCandidates` 和 `needsOrganizationSelection`，模型需让用户确认组织后再用 `organizationId` 继续查询。
- 打开详情：`device_instance_search` 返回候选时附带 `detailLink` 和 `markdownLink`，链接形如 `#/iot/device/Instance/detail/<deviceId>`，复制到地址栏也能直接访问。用户点击历史 `#route=device%2FInstance%2FDetail&menu=device%2FInstance&id=<deviceId>` 参数式链接时，对话组件会兜底规范化为真实 hash 路由；详情页不是可见菜单时，不再复用 `navigateToMenu` 做隐式猜测。
- 固定工作流：设备实例 provider 通过 `workflowGuides` 暴露“特定设备请求路由”。当用户请求需要具体设备对象作为上下文、且当前不在设备详情 subject 中时，模型先通过 `agent_workflow_guide` 获取流程，再执行 `device_instance_search` 定位候选；无候选时说明未匹配，多候选时让用户选择，单一明确候选时回复该候选的 `markdownLink` 让用户点击进入详情。该设计避免为“分析/排查/查看”等具体措辞做特调，也避免把组织、产品、状态等关联条件写成特定问法。
- 首页到详情交接：首页智能体只负责设备定位、轻量列表/数量回答和详情入口交接。涉及单台设备的运行分析、告警、日志、接入或云边诊断时，回复应简短说明已定位目标设备，给出详情链接，并提示进入详情后由设备详情助手基于该设备上下文继续诊断；不要在首页展开设备详情智能体的内部取证流程，也不要替用户自动导航。
- Workflow Guide 边界：`workflowGuides` 只描述“何时适用、如何取证、输出结果”，不承载全局回答语气、Markdown 格式、安全策略或 provider 修补提示。`agent_workflow_guide` 的工具结果面向模型内部取证建议，返回 `guidance/evidencePlan/expectedResult` 等业务化字段，不返回原始 `tool`、workflow id、`steps.tools` 或 `inputs`，最终回答策略由后端通用智能体统一追加。
- 全局触发：设备实例 provider 会在非设备列表页补充全局 system prompt，用户在首页或其它页面提出具体设备对象相关请求时，模型按固定工作流搜索候选并回复受控详情链接。
- 页面专用助手切换：当前实现仍采用同一个全局气泡承载当前 active client；设备详情的 `deviceDetailChat` 会覆盖首页 `iotHome`。若要支持在设备详情里切回通用首页助手，建议作为下一阶段“助手范围切换”实现：同一抽屉中切换“通用助手 / 当前页面助手”，并分别维护 clientId、subject、未读计数、会话参数和返回入口，不建议同时展示两个气泡。
- 页面专用助手预占位：带页面级智能体的路由应在 `meta.pageAgentClientId` 或 `meta.aiAgentClientId` 中声明 clientId；全局首页助手在同步前读取该声明并调用 `prepareAgentConversation(...)`，避免刷新页面时 `iotHome` 在页面详情数据返回前抢先打开。页面组件拿到业务上下文后再调用 `queryAgent(...)` 补齐 subject、工具和欢迎语；卸载时使用 `releaseAgentConversation(clientId)` 只释放自己的助手，避免误关其它页面刚接管的助手。
- 页面范围隔离：同一个 `clientId` 可以同时服务多个业务对象或项目实例。页面专用助手只需要传 `subjectType/subjectId/subjectName` 等业务 subject；公共 `AiChat` 会在当前浏览器 tab 内生成随机 `handoffKey`，并用它隔离前端 handoff 记录与会话组件实例。subject 只作为当前 tab 中查找随机 key 的业务锚点，以及后端历史会话查询与自动恢复的过滤条件，不作为 localStorage 的 handoff key。两个窗口即使打开同一个设备或项目，也会因为 tab 内随机 key 不同而各自维护前端移交状态；刷新当前 tab 时通过 `sessionStorage` 保留这条绑定。handoff 记录固定 30 分钟有效，用户发送预填内容后立即删除 localStorage 记录和当前 tab 指针。
- 业务回执：handoff 只负责前端一次性续接，不负责让首页模型长期记住业务对象。首页工具在创建或定位业务对象后，应在工具结果中返回稳定的 business receipt，例如 `subjectType/subjectId/subjectName`、业务对象摘要、目标菜单/路由和可点击链接；后续用户说“刚才创建的规则 / 这个设备 / 这个项目”时，模型优先使用工具结果里的 subject 继续定位，而不是依赖随机 `handoffKey`。

## 告警仪表盘能力结论

- 告警仪表盘工具注册：`runtime-ui/modules/rule-engine-manager-ui/register.ts` 通过 `homeAgentProviders` 暴露 `rule-engine/DashBoard` 对应的 `views/DashBoard/homeAgentProvider.ts`，页面进入时也通过 `useHomeAgentCapabilityProvider` 主动注册同一个 provider。
- 统计契约：告警趋势和排行工具基于后端 `DashboardMeasurementRequest` 的真实能力，而不是复刻页面快捷按钮。趋势固定使用 `dashboard=alarm`、`object=record`、`measurement=trend`、`dimension=agg`；排行固定使用 `measurement=rank`；可传 `from/to/time/format/limit/targetType/targetId/alarmConfigId`，其中 `from/to` 支持后端 `TimeUtils.parseDate` 能解析的 `now-1d`、`now-7d`、`now` 和绝对时间。
- 对象类型：当用户提到告警对象但不确定 `targetType` 时，先用 `alarm_dashboard_get_target_types` 读取后端当前支持的对象类型，不在提示词里写死一组对象类型。
- 默认口径：用户未给时间时，工具只使用最近 24 小时作为可用默认值；这不是能力限制。模型应优先采用用户提供的自定义 `from/to/time/format/limit`，并在输出中说明实际查询范围。

## 设备/产品领域通用只读能力计划

- 目标：把设备详情中适合跨页面复用的基础智能体能力暴露为首页通用 provider，供规则编排助手在生成规则、填充默认测试输入、诊断规则运行结果时直接查询设备/产品上下文。
- owning module：`runtime-ui/modules/device-manager-ui`。新增设备领域 provider 与只读客户端工具，继续由 `runtime-ui/jetlinks-web-core` 的 `homeAgentProviders` 动态加载机制聚合；规则编排助手通过已有 `useRuleEditorSharedAgentTools.ts` 复用这些只读工具。
- 代码落点：`views/device/Domain/homeAgentProvider.ts` 负责注册通用领域能力；`views/device/Domain/agentDeviceDomainTools.ts` 负责显式 `deviceId/productId` 的工具实现；设备模块中英文 i18n 补充工具文案。
- 能力范围：暴露 `device_model_get`、`device_metadata_search`、`device_latest_properties`、`device_property_history_summary`、`device_property_history`、`device_property_aggregate` 等只读工具。物模型工具支持设备或产品；属性最新值、历史和聚合工具必须传 `deviceId`。
- 不做：不把 `device_function_invoke`、设备控制、写配置、远程文件读取、边缘深度诊断等需要当前详情上下文或可能产生副作用的能力放入通用 provider；不调整 Markdown 链接处理、路由链接或规则编辑器后端接口。
- 权限边界：provider 只在当前账号可见 `device/Instance` 或 `device/Product` 菜单时返回能力；工具执行时再次按实际入参检查设备/产品菜单权限，避免只因模块文件存在就暴露越权查询。
- 验证：校验设备模块中英文 JSON；对新增 provider 和工具执行 `diff --check`；运行 `pnpm -C runtime-ui build:modules device-manager-ui`，并补充规则编排模块构建验证以确认共享工具接入不破坏规则助手。

## 风险与边界

- 菜单能力只暴露当前用户已加载和可见的菜单，不输出完整路由表或权限按钮明细。
- 首页工具结果需要保持小体积，避免会话初始化或工具回传膨胀。
- 动态 provider 注册后，正在打开的首页会话需要刷新参数；本次先在首页视图、菜单初始化变化时刷新。
- 写操作、设备控制等强副作用能力仍应放在对应页面或后端工具中，首页仅做发现、导航和跨能力路由。
