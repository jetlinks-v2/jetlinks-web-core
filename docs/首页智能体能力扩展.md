# 首页智能体能力扩展计划

## 当前结论

首页智能体不应简单复制设备详情页的专用工具实现，而应复用同一套会话参数契约，将 `iotHome` 作为运行时首页的能力路由入口。首页负责汇聚当前用户可见菜单、可用功能和 provider 主动注册的客户端工具；具体业务模块通过 provider 注册自己的能力说明和工具。

## 影响范围

- owning module：`runtime-ui/jetlinks-web-core`
  - 新增首页智能体能力注册与聚合运行时。
  - 复用 `layout/components/AiChat/clientTools.ts` 的工具描述、确认与结果裁剪能力。
- 接入入口：`runtime-ui/jetlinks-web-core/src/layout/BasicLayoutPage.vue`
  - 全局布局在没有页面专用智能体时恢复 `iotHome` 默认入口，并传入首页上下文、工具、系统提示和链接处理器。
- 参考模块：`runtime-ui/modules/device-manager-ui`
  - 设备“首页”菜单只作为普通菜单能力被首页智能体发现，不再直接挂载 `iotHome`。
- 不调整后端 `jetlinks-ai-agent` 协议，不改 `deviceDetailChat` 设备详情页现有工具实现。

## 最佳实践依据

- MCP 将工具、上下文资源、客户端交互能力分开建模；工具通过描述和 schema 让模型发现和调用，并建议工具暴露、调用过程、人工确认在 UI 中清晰可见。
- MCP 的客户端能力强调由客户端控制用户交互与数据边界，动态补充信息时使用结构化交互，而不是一次性把所有上下文塞进提示词。
- OpenAI Apps SDK 的工具 descriptor 推荐声明结构化输出、只读/破坏性等注解，以及工具调用中的状态元数据；这些原则对应到本项目就是：只读发现工具默认开放，导航/写操作保留明确确认或用户点击。

## 设计入口

### 1. 首页能力 provider

每个模块可注册一个首页能力 provider，包含：

- `id`：provider 唯一标识。
- `getCapabilities(context)`：返回菜单、功能、其他智能体、向导等能力摘要。
- `getClientTools(context)`：返回该模块给首页智能体暴露的客户端工具。
- `getWorkflowGuides(context)`、`getPromptExamples(context)`、`getSystemPromptLines(context)`：可选补充对话引导。

### 2. 首页聚合运行时

首页聚合运行时负责：

- 从菜单 store 读取当前账号可见菜单，压缩为可搜索的能力目录。
- 合并 provider 注册的能力和工具。
- 生成 `clientTools`、`clientToolHandler`、`clientToolsName`、`clientToolsDescription`。
- 生成 `systemPrompt`、`openingStatement`、`promptExamples`、`workflowGuides`。
- 提供受控 Markdown 深链，如 `#menu=device%2FInstance`，点击时通过菜单 store 跳转。

### 3. 默认内置工具

- `home_agent_get_context`：查看当前首页视图、路由、菜单数量和能力数量。
- `home_agent_search_capabilities`：按关键词、能力类型搜索菜单/功能/智能体。
- `home_agent_open_menu`：打开已授权菜单，导航前要求用户确认。

## 实施步骤

1. 在 `jetlinks-web-core` 新增首页能力注册和运行时文件。
2. 在全局布局 `BasicLayoutPage` 接入 `iotHome` 聚合参数；首页能力目录只接收菜单和 provider 声明，不再把 pagePoint 挂载点配置自动转成可发现能力。
3. 为首页智能体添加受控菜单深链处理。
4. 补充国际化文案或沿用现有 AI 对话文案。
5. 运行 `pnpm -C runtime-ui -F jetlinks-web-core build` 验证类型和打包。

## 当前页能力推荐优化计划

- 目标：首页智能体推荐问题根据当前路由调整；在 `iot/home` 一类首页展示轮换推荐，在业务页面优先展示当前页注册的能力。
- 影响范围：`homeAgentCapabilities.ts`、`useGlobalHomeAgent.ts`、`device-manager-ui/views/device/DashBoard`。
- 不做：不让所有页面自动执行写操作；不从未声明的页面 DOM 中猜测工具参数；不新增后端接口。
- 实施：provider 注册/注销时触发首页智能体参数刷新；设备管理/仪表盘页面注册“分析设备消息聚合”能力和只读客户端工具，工具复用现有 `/dashboard/_multi` 按今日、近 24 小时、近 7 天、近 30 天或自定义时间范围查询消息量、趋势和峰值并返回结构化摘要。
- 动态加载：各业务模块在自身 `register.ts` 中用本模块相对路径扫描能力文件，并通过 `moduleRegistry` 的 `homeAgentProviders` 资源暴露给 core；key 建议使用路由能力编码（如 `device/DashBoard`），value 为 loader。能力文件可通过 `default`、`homeAgentCapabilityProvider` 或 `homeAgentCapabilityProviders` 暴露 provider；不再要求用户先进入对应页面，也不加载页面 SFC 生命周期。
- 路由能力加载：内置 `home_agent_load_route_capabilities` 只导入 provider 文件，不进入页面；全局同步阶段会预加载轻量 provider，确保首页首轮也能看到模块声明能力。provider 仍需自行按 `context.findMenu(...)` 或业务权限判断是否返回工具，避免仅因模块文件存在就暴露未授权能力。
- 组件主动注册：已进入的页面可调用 `useHomeAgentCapabilityProvider(provider)` 主动注册更贴近当前页面状态的 provider；registry 对同一 provider id 使用栈式覆盖，页面卸载后会恢复模块级 provider，避免把首页可发现能力一并注销。
- 风险：自动把每个页面变成工具能力需要页面声明工具边界，本次先落一个可复用 provider 模板，避免把普通路由误判为可执行工具。
- 验证：检查 i18n JSON、运行 `pnpm -C runtime-ui -F jetlinks-web-core build`。

- 不做：不新增后端接口；不绕过菜单权限直接跳转隐藏路由；不在首页通用智能体中暴露设备控制、删除、下发等强副作用能力；不把关闭浮窗等同于销毁后端会话。
- 实施：
  1. 在首页能力聚合层增加通用可见性过滤：`menuCode` / `routeName` / `path` 指向菜单的 feature、agent、tool 类能力，默认必须命中 `context.findMenu(...)`；业务 provider 仍可用 `getCapabilities/getClientTools` 做更细粒度条件判断。
  2. 为 `device/Instance` 增加首页能力 provider，提供只读 `device_instance_search` 工具，复用 `/device-instance/_query` 按关键词、产品、状态分页返回候选，并在结果中给出 `#menu=device%2FInstance` 和可继续执行的详情打开工具参数；若需要弹出选择页，优先作为后续可选增强，不在首版新增复杂选择弹窗。
  3. 扩展通用 `AiChat` 气泡参数，支持页面传入 icon / iconBadge / class / tooltip；设备详情页通过 `deviceDetailChat` 参数传专用图标，首页 `iotHome` 保持通用图标。
  4. 保持 `AiChatDrawer` 关闭只隐藏不卸载会话组件；让 `AgentConversation` 在收到 socket 消息、且当前浮窗未打开时向外抛出隐藏消息增量，由 store 记录到气泡 badge；打开浮窗后清零。

## 设备搜索与页面专用助手切换结论

- 设备实例工具注册：`runtime-ui/modules/device-manager-ui/register.ts` 通过 `homeAgentProviders` 暴露 `views/device/Instance/homeAgentProvider.ts`，全局首页智能体通过 `loadHomeAgentCapabilityProviders({ loadAll: true })` 预加载轻量 provider。`device_instance_search` 只在当前账号可见 `device/Instance` 菜单时暴露。
- 搜索契约：`device_instance_search` 按设备列表页已有查询条件类推，支持 `keyword/idOrName/id/name/productId/productName/state/deviceType/describe/classifiedId/accessId/accessProvider/organizationId/organizationName/organizationKeyword`。仅智能体设备搜索工具请求使用 `QueryParamEntity.filter` 表达式，不在前端手工拼 `terms`，也不追加默认 `sorts`，避免影响智能体查询执行计划；设备实例列表页仍保持自身查询和排序逻辑。`keyword` 只生成 `{"id$like":"%关键词%","$or$name$like":"%关键词%"}`；当用户输入无法判断是设备 ID 还是名称时，模型应使用 `keyword` 或 `idOrName` 做 ID/名称模糊搜索；工具内部会把 `like` 条件统一写成 `%关键词%`。数量类问题使用返回的 `total`，可把 `limit` 设小以减少结果体积。
- 关联条件：涉及“某组织/部门下的设备数量或列表”时，模型不应直接猜组织 ID。传入 `organizationName` 或 `organizationKeyword` 后，工具会先查 `/organization/_query/no-paging` 解析组织候选；唯一或精确匹配时再用设备列表同款 `id$dim-assets` 资产维度条件查询设备。多个组织候选时，工具返回 `organizationCandidates` 和 `needsOrganizationSelection`，模型需让用户确认组织后再用 `organizationId` 继续查询。
- 打开详情：`device_instance_search` 返回候选时附带 `detailLink` 和 `markdownLink`，链接形如 `#route=device%2FInstance%2FDetail&menu=device%2FInstance&id=<deviceId>`。用户点击后由 `HomeAgentCapabilityContext.navigateToRoute(...)` 打开详情；详情页不是可见菜单时，不再复用 `navigateToMenu` 做隐式猜测。
- 固定工作流：设备实例 provider 通过 `workflowGuides` 暴露“特定设备请求路由”。当用户请求需要具体设备对象作为上下文、且当前不在设备详情 subject 中时，模型先通过 `agent_workflow_guide` 获取流程，再执行 `device_instance_search` 定位候选；无候选时说明未匹配，多候选时让用户选择，单一明确候选时回复该候选的 `markdownLink` 让用户点击进入详情。该设计避免为“分析/排查/查看”等具体措辞做特调，也避免把组织、产品、状态等关联条件写成特定问法。
- Workflow Guide 边界：`workflowGuides` 只描述“何时适用、如何取证、可用工具、输出结果”，不承载全局回答语气、Markdown 格式、安全策略或 provider 修补提示。首页 provider 的 system prompt 只保留当前页面能力上下文，设备定位、仪表盘消息聚合等多步流程放入 `agent_workflow_guide` 返回的结构化 guide。
- 全局触发：设备实例 provider 会在非设备列表页补充全局 system prompt，用户在首页或其它页面提出具体设备对象相关请求时，模型按固定工作流搜索候选并回复受控详情链接。
- 页面专用助手切换：当前实现仍采用同一个全局气泡承载当前 active client；设备详情的 `deviceDetailChat` 会覆盖首页 `iotHome`。若要支持在设备详情里切回通用首页助手，建议作为下一阶段“助手范围切换”实现：同一抽屉中切换“通用助手 / 当前页面助手”，并分别维护 clientId、subject、未读计数、会话参数和返回入口，不建议同时展示两个气泡。

## 风险与边界

- 菜单能力只暴露当前用户已加载和可见的菜单，不输出完整路由表或权限按钮明细。
- 首页工具结果需要保持小体积，避免会话初始化或工具回传膨胀。
- 动态 provider 注册后，正在打开的首页会话需要刷新参数；本次先在首页视图、菜单初始化变化时刷新。
- 写操作、设备控制等强副作用能力仍应放在对应页面或后端工具中，首页仅做发现、导航和跨能力路由。
