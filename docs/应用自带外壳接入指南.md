# 应用自带外壳接入指南

这份文档教你把一个业务应用（比如养老、园区、消防）接进运行时，让它用自己的布局和样式，而不是被塞进宿主的默认页面框架里。

照着做就行，每一步都有现成代码可以抄。大约 30 分钟能跑出第一个能看的页面。

---

## 一、先搞明白三件事

别看代码，先理解概念，不然后面每一步你都不知道自己在干嘛。

**第一件：宿主。** `runtime-ui/jetlinks-web-core` 就是宿主。它负责登录、菜单、权限、路由、请求、主题。所有应用都跑在它里面。

**第二件：模块。** `runtime-ui/modules/` 下面每一个文件夹就是一个模块，比如 `jetlinks-eldercare-ui`、`fire-control-saas-ui`。模块给宿主"贡献"东西：页面、菜单、接口、组件。

**第三件：外壳。** 平时宿主会给应用套一个默认的页面框架（就是左边有菜单、上边有头像那个）。外壳就是"我不想用你这个框架，我自己的页面自己画"。

串起来的顺序是这样：

```
用户登录 → 进入某个业务应用（URL 上带 applicationScope=应用ID）
        → 宿主知道"现在是应用运行态"
        → 宿主去问每个模块：你有没有为这个应用准备外壳？
        → 谁说自己命中（match 返回 true），就用谁的外壳
        → 都没说自己命中，就用默认外壳
```

所以关键就一句：**你在模块里写一段代码，告诉宿主"我就是这个应用的外壳"，并且给出一个判断条件，让宿主知道什么时候该用你。**

---

## 二、什么时候需要做这件事

需要做：

- 你的应用要自己画整个页面框架（自己的侧边栏、自己的顶部栏、自己的品牌色区域）。
- 你的应用页面里要放一些"不属于普通后台页面"的东西，比如驾驶舱、全屏大屏、值班面板。

不需要做：

- 你只是给宿主加几个普通页面。那就按 `contentPanelOverrides` 那套来，别碰外壳。
- 你的应用长得跟默认后台差不多，只是换个 logo 换个名字。改配置就行，别写外壳。

**别为了"显得专业"就写外壳。** 外壳一旦写出来，菜单、路由、权限这些你都得自己接一遍，工作量翻倍。

---

## 三、模块目录长什么样

先看一个真实的最小例子（`modules/jetlinks-eldercare-ui`）：

```
modules/jetlinks-eldercare-ui/
├── index.ts            ← 模块入口，必须有，这是宿主找到你的唯一入口
├── baseMenu.json       ← 菜单数据，必须有（除非你的模块完全不要菜单）
├── baseMenu.ts         ← 菜单的包装层，必须有（和 baseMenu.json 成对出现）
├── package.json        ← 必须有
├── register.ts         ← 可选，用来注册接口/组件给别的模块用
└── views/              ← 你的页面，随便组织
```

两个硬性规则，记牢：

1. **目录里的 `index.ts` 必须 `export default` 一个对象。** 宿主是靠 `import.meta.glob('../../../modules/*/index.ts')` 扫描的，没有 default 导出，你这个模块直接被丢弃，不报错，静默消失。
2. **`baseMenu.json` 和 `baseMenu.ts` 要么都有，要么都没有。** 只写 json 不写 ts，菜单不会被收集。

## 四、接入步骤

### 步骤 1：建目录，写 package.json

目录名统一 `<名字>-ui`，放在 `runtime-ui/modules/` 下面。

```bash
cd runtime-ui/modules
mkdir my-app-ui
```

`package.json` 抄这个改：

```json
{
  "name": "my-app-ui",
  "id": "my-app",
  "version": "1.0.0",
  "description": "我的应用 UI 模块",
  "main": "index.ts",
  "private": true,
  "scripts": {
    "dev": "pnpm --filter jetlinks-web-core dev -- --module-name my-app-ui",
    "build": "pnpm --filter jetlinks-web-core build -- --module-name my-app-ui"
  },
  "dependencies": {},
  "peerDependencies": {}
}
```

`name` 是目录名，`id` 是给人看的短名，两个都填成一样的习惯更好认。

### 步骤 2：写菜单 baseMenu.json

这是最容易被坑的一步，**重点在这里**。

```json
[
  {
    "id": "my-app-dashboard-menu",
    "code": "myApp/Dashboard",
    "name": "仪表盘",
    "url": "/myApp/dashboard",
    "owner": "app",
    "icon": "DashboardOutlined",
    "sortIndex": 1,
    "i18nMessages": {
      "name": {
        "zh_CN": "仪表盘",
        "en_US": "Dashboard"
      }
    },
    "showPage": ["my-app-dashboard"],
    "permissions": [
      { "permission": "my-app-dashboard", "actions": ["query"] }
    ],
    "buttons": []
  }
]
```

**`showPage` 别漏。** 它是菜单能否出现在候选和被下发的开关：

- 初始化页和「菜单设置」页都按 `showPage` 过滤。叶子菜单不写 `showPage`，会被直接丢掉，连候选都看不到。
- 值必须和后端注解扫描出的权限 id 一致（`GET /system/resources/permission` 返回的那批 id）。
- 和 `permissions` 不是一回事：`showPage` 管"这个菜单能不能出现"，`permissions` 管"菜单里的按钮要不要给"。两个都写，值通常取同一个权限 id。

**`owner` 必须是 `"app"`。** 这句话值一万个字：

- 宿主进入应用运行态时，只向服务端要 `owner = "app"` 的菜单。
- 你写成 `"iot"` 或别的，你的菜单根本不会下发，`match` 永远判断不到，外壳永远不生效。
- **每一层菜单都要写 `owner: "app"`。** 服务端保存时其实会把 owner 刷到整棵树，所以少写几层理论上也能跑；但仓库里所有应用模块都是一层层写全的，你跟着写，别当特例，省得以后排查时怀疑人生。

`code` 会被用作路由名，也是后面 `match` 里最常用的判断依据。**起个好记、不容易改的名字**，因为一旦上线再改，外壳就会静默失效。

### 步骤 3：写 baseMenu.ts

就是个包装，把模块身份塞进每条菜单的 `options.appName`，再标个 `runtime: true`。直接抄：

```ts
import baseMenu from './baseMenu.json'
import packageInfo from './package.json'
import type { MenuItem } from '@jetlinks-web-core/types/module'

const withModuleOptions = (menus: MenuItem[]): MenuItem[] => menus.map((item) => ({
  ...item,
  children: item.children ? withModuleOptions(item.children) : undefined,
  options: {
    appName: packageInfo.id || packageInfo.name,
    ...item.options,
  },
  runtime: true,
}))

export default () => withModuleOptions(baseMenu as MenuItem[])
```

### 步骤 4：写你的外壳组件

外壳就是一个普通 Vue 组件。**唯一死规定：里面必须渲染一次路由出口**，不然你的页面全都显示不出来。

两种写法，选一个：

**推荐写法**（带加载骨架，跟默认布局体验一致）：

```vue
<template>
  <div class="my-app-shell">
    <aside class="my-app-shell__sider">
      <!-- 你自己的侧边栏 -->
    </aside>
    <main class="my-app-shell__content">
      <PageRouteView />
    </main>
  </div>
</template>

<script setup lang="ts" name="MyAppShell">
import PageRouteView from '@jetlinks-web-core/components/PageRouteView/index.vue'
</script>
```

**简单写法**（不要骨架）：

```vue
<template>
  <div class="my-app-shell">
    <router-view />
  </div>
</template>

<script setup lang="ts" name="MyAppShell">
</script>
```

就这两行，别多想。一开始别急着做复杂的侧边栏，先把 `<PageRouteView />` 渲染出来，看到页面能显示，再慢慢加。

**外壳只能有一个根元素。** 这条很重要，写错了你会排查很久：

宿主会给外壳挂 `class="jl-app-scope"` 和 `data-jl-app="..."`。Vue 只会在**单根节点**组件上自动继承这些属性；如果你的模板是这种多根写法：

```vue
<!-- ❌ 多根，class 会被丢弃，控制台还会警告 -->
<template>
  <div class="my-sider" />
  <div class="my-content"><PageRouteView /></div>
</template>
```

`jl-app-scope` 根本挂不上去，你的 `.jl-app-scope` 样式全部失效，控制台还会报 `Extraneous non-props attributes ... fragment root nodes`。正确写法是外面再包一层：

```vue
<!-- ✅ 单根 -->
<template>
  <div class="my-app-shell">
    <div class="my-sider" />
    <div class="my-content"><PageRouteView /></div>
  </div>
</template>
```

几个你一定会问的点：

- **外壳能拿到什么参数？** 什么参数都没有。宿主只负责挂载，不传 props。要数据自己从 store 里取，比如 `useMenuStore().siderMenus` 拿菜单、`useUserStore()` 拿用户。
- **外壳会拿到 class 吗？** 会。宿主会给你的根元素加一个 `jl-app-scope` 类，还会加 `data-jl-app="应用ID"`。这两个东西后面做样式要用到。
- **能拿到宿主的路由实例吗？** 能，`useRouter()` 照常用，外壳和页面在同一个 Vue 应用里。

### 步骤 5：在 index.ts 里声明外壳（最关键的一步）

先写 `index.ts` 的骨架：

```ts
import { moduleRegistry } from '@jetlinks-web-core/utils/module-registry'
import registerSetting from './register'
import { name } from './package.json'

const routerModules = import.meta.glob('./views/**/index.vue')

const getAsyncRoutesMap = () => {
  const modules: Record<string, unknown> = {}
  Object.keys(routerModules).forEach((item) => {
    const code = item.replace('./views/', '').replace('/index.vue', '')
    modules[code] = routerModules[item]
  })
  return modules
}

const register = () => moduleRegistry.register(name, registerSetting)

export default {
  priority: 10,
  getAsyncRoutesMap,
  getExtraRoutesMap: () => ({}),
  getComponents: () => ({}),
  register,

  // 👇 就是这一段，其他都是常规配置
  getApplicationShell: () => ({
    component: () => import('./shells/index.vue'),
    match: ({ hasMenu }) => hasMenu('myApp/Dashboard'),
  }),
}
```

逐行解释：

| 这行 | 什么意思 |
| --- | --- |
| `priority: 10` | 优先级。数字大的赢。你自己一个应用一般不会跟别人抢，写 10 就行；如果发现别的模块也在抢，把数字调大。 |
| `component` | 你的外壳组件，用 `() => import(...)` 懒加载，别直接 `import`，不然整个应用首屏都会带上你的样式。 |
| `match` | 判断函数。宿主把当前应用的菜单情况传给你，你返回 `true` 就说"这个应用归我管"。 |
| `hasMenu('myApp/Dashboard')` | 在当前应用的菜单里找这个 code，找到返回 true。 |

**`match` 里能查的 key 只有三种**，随便用哪个，只要你的菜单里确实有：

1. 菜单的 `code`，比如 `myApp/Dashboard` —— **最推荐**，最直白。
2. `componentCode`（菜单 `options.meta.componentCode`，或 `options.componentCode`），页面复用的时候用这个。
3. `routeName`（菜单 `options.routeName`，或 `options.meta.routeName`）。

**注意：路由路径（`/myApp/dashboard`）查不到。** 别写成 `hasMenu('/myApp/dashboard')`，它永远返回 false，而且不报错。

如果你有多个入口菜单，就 `||` 串起来：

```ts
match: ({ hasMenu }) =>
  hasMenu('myApp/Dashboard') || hasMenu('myApp/DeviceList'),
```

**写完之后自检一遍**：`match` 里写的这些 code，必须真的出现在你 `baseMenu.json` 里。写错一个字母，外壳就是不生效，而且**不会报错**（只有控制台一行 warning）。

### 步骤 6：把 register.ts 补上

如果暂时没有要给别的模块用的东西，写个空壳就行：

```ts
export default {
  apis: {},
  components: {},
}
```

`register.ts` 不会自动加载，必须在 `index.ts` 里 `import` 进来，再通过 `moduleRegistry.register()` 注册。空着也要有，因为 `index.ts` 里引用了它。

### 步骤 7：本地跑起来

```bash
cd runtime-ui
pnpm -F jetlinks-web-core dev -- --module-name my-app-ui
```

`--module-name` 后面填的是**目录名**（`my-app-ui`），不是 `package.json` 里的 `id`。参数传中文目录名会挂，别试。

**这里有个坑要先说清楚：** `--module-name` 是白名单模式，**只有**你指定的模块会被加载，其他模块的源码会被替换成空文件。所以如果你的模块 import 了别的模块（比如 `@device-manager-ui/api/instance`），单模块开发时会报"xxx is not exported"。解决办法是把依赖也带上，逗号分隔：

```bash
pnpm -F jetlinks-web-core dev -- --module-name my-app-ui,device-manager-ui
```

只想跑全量、不在乎启动慢的话，就别加 `--module-name`，直接 `pnpm -F jetlinks-web-core dev`。

打开浏览器之后，还要进到"应用运行态"才能看到外壳。两种办法：

**办法一：从界面点进去。** 登录后如果账号有应用角色，会自动进第一个应用；或者在顶部应用切换器里选你的应用。

**办法二：直接敲 URL。** 格式是这样：

```
http://localhost:<端口>/<应用ID>/#/<页面路径>?applicationScope=<应用ID>
```

比如：

```
http://localhost:9200/2110624290785468416/#/myApp/dashboard?applicationScope=2110624290785468416
```

`<应用ID>` 是后端 `s_business_application` 表里的那个 ID，一长串数字。

## 五、怎么确认你真的接进去了

按顺序查，一条一条来：

**第一步：看 URL。** 必须带 `?applicationScope=xxx`。没有这个参数，宿主根本不知道你在应用运行态，走的是项目/租户分支，你的外壳永远不生效。

**第二步：看控制台 warning。** 宿主在你没命中时会打一条：

```
[Application Shell] Module "my-app-ui" declared a shell but did not match
the current application menus; falling back to the default layout.
```

看到这条，说明：代码被加载了，但是 `match` 没命中。去查你 `match` 里的 code 和 `baseMenu.json` 是不是对得上。**这条 warning 每个模块只会打一次**，刷新页面才会再打。

**第三步：看菜单有没有下发。** F12 → Network，找 `/menu/user-own/tree` 这个请求，看返回里有没有你的菜单。没有的话，八成是 `owner` 写错了，或者菜单根本没初始化进数据库。

**第四步：看 DOM。** 外壳挂载成功的话，你的根元素上会有 `class="jl-app-scope"` 和 `data-jl-app="应用ID"`。用审查元素点一下就能看到。

**第五步：如果两个模块都命中**，控制台会有：

```
[Application Shell] Module "xxx" also matched but "yyy" wins by priority (10 > 0).
```

这时候要么删掉多余的那个声明，要么调 `priority` 明确谁说了算。

## 六、菜单怎么进到数据库（这步最容易卡住）

代码写完了，菜单不一定出现。因为**你写的 `baseMenu.json` 不会自动生效**，它只是"初始化数据"，得先被推送到服务端菜单表，宿主运行时才能查到。

先理解这条链路：

```
baseMenu.json（你写的，躺在代码里）
   ↓ 只在初始化时推送
PATCH /menu/{owner}/_all   ← 按 owner 整棵覆盖
   ↓
服务端菜单表（s_menu）
   ↓ 应用运行态查询
POST /menu/user-own/tree  { owner: "app" }
   ↓
宿主拿到的菜单 → hasMenu() 能判断到你 → 外壳生效
```

### 你的 `owner` 决定推到哪一堆

同一个接口，`owner` 不同推的是不同的菜单集合：

- `owner: "app"` → 应用菜单，只有应用运行态（带 `?applicationScope=`）才会查。
- `owner: "iot"`（`VITE_APP_NAME`，默认值）→ 项目/租户端菜单。

所以你写 `owner: "app"` 的模块菜单，跟项目端那套是完全隔离的两堆数据。

### 警告：`/menu/{owner}/_all` 是"先删后插"

这个接口保存时会把该 `owner` 下**所有**菜单先删光，再插入你这次提交的整棵树。也就是说它不是"增量更新"，是"整堆替换"。

后果：

- 你只想加一个菜单，却调了这个接口，就会把该 owner 下其他应用（养老、消防、园区）的菜单一起删掉。
- `/init-home` 初始化页走的就是这个接口，所以**已有环境里不要随便重跑初始化**。

### 新环境（还没初始化过）

直接走初始化流程：用管理员账号访问 `/init-home`，页面会把所有模块的 `baseMenu`（包括你 `owner: "app"` 的那部分）分组推上去。

进去之后到「菜单」那一步，确认能勾到你的菜单，再提交。

### 已有环境（已经在跑了）

**用「菜单设置」页同步，这条是唯一正确的路。**

先说结论：**别用「菜单详情 → 新增」去建应用菜单。** 那个表单里根本没有 `owner` 选项，提交时会用默认值 `iot`，建出来的是项目菜单，不是应用菜单。很多人卡在这里一下午。

正确操作：

```text
系统设置 → 菜单管理 → 右上角「菜单设置」
```

进去之后：

1. 上面有两个 tab：`iot`（项目/租户）和 `app`（应用）。选 `app`。
2. 左边树里会列出**当前构建里所有模块的 `baseMenu`**，包括你新写的那个。你的菜单默认是**未勾选**状态。
3. 勾上你要开放的菜单，可以拖拽调整父子顺序。
4. 点保存。

保存时会 `PATCH /menu/app/_all`，把 `app` 这一堆整棵替换成"服务端已有 + 本地候选"合并后的结果。所以：

- 你新加的菜单会被插进去。
- 其他应用（养老、消防、园区）已经在库里的菜单**不会丢**，因为它是先把服务端已有的树读出来再合并。
- 之前被关掉（未勾选）的菜单也还在，只是 `show: false`，随时可以再勾回来。

⚠️ 两个前提：

- 这个入口只对 `admin` 账号显示（判断条件是用户名等于 `admin`）。用普通管理员账号看不到按钮。
- 页面里的候选来自当前构建的 `modules/*/baseMenu.ts`，所以**代码必须先构建/部署，才能在候选里看到你的菜单**。

### 如果你就是要建一条独立的应用菜单

极少见，但如果真有（比如某个应用专属的临时菜单），只能直接调接口：

```http
POST /menu
{
  "code": "myApp/Temp",
  "name": "临时页面",
  "url": "/myApp/temp",
  "owner": "app",
  "parentId": "<父菜单ID>",
  "sortIndex": 99
}
```

请求体里必须显式带 `"owner": "app"`，不带就会被存成 `iot`。

建完记得给角色授权，不然菜单下发了但用户看不到。

### 改完 `code` 怎么办

如果你改了菜单 `code`：

1. 服务端那条菜单也要改（否则宿主查到的还是旧 code）。
2. `match` 里的判断同步改。
3. 两处都改完，清理浏览器缓存后重新进入应用。

只改一边 = 外壳静默失效，常见事故。

## 七、样式规则（很重要，不遵守会互相污染）

宿主所有模块的 CSS 最后会被打进同一个文件（`cssCodeSplit: false`），所以模块之间**没有天然的样式隔离**。你的样式可能跑到别人的页面上，别人的也可能跑进你的。

三条规矩，遵守就没事：

**1. 所有全局样式都写在 `.jl-app-scope` 下面。**

```less
.jl-app-scope {
  .my-app-shell {
    background: #0b1220;
  }
}
```

因为宿主会给你的外壳根元素加 `jl-app-scope` 这个类，所以这样写等于"只在我自己的地盘生效"。

**2. 不要写 `html`、`body`、`:root`、`.ant-*` 这些全局选择器。**

```less
/* ❌ 千万别这么写，会把整个后台都改掉 */
body { background: #000; }
:root { --primary-color: #f00; }
.ant-btn { border-radius: 0; }

/* ✅ 这么写 */
.jl-app-scope .ant-btn { border-radius: 0; }
```

**3. 不要改根元素的主题变量。**

`document.documentElement.style.setProperty(...)` 这类写法会污染别的应用和项目端。要局部换色，用 `ConfigProvider` 包一层，或者直接在自己的作用域里覆盖 CSS 变量。

如果你确实需要一套完全独立的设计体系（连 Ant Design 都不想用），那外壳这条路不合适，得走 iframe 隔离。找架构组聊。

---

## 八、别做的事

- **别在 `match` 里写异步逻辑。** 它必须是同步返回 boolean。要异步数据先在外面准备好。
- **别在 `component` 里直接 `import`。** 必须 `() => import(...)`，否则会拖慢所有应用的启动。
- **别在外壳里再套一层 `BasicLayoutPage`。** 你会套两层菜单。
- **别改别人的 `priority` 来抢外壳。** 要抢就调自己的，并且最好在 PR 里说清楚为什么。
- **别把 `owner` 写成 `"iot"` 或 `"cloud"`。** 应用运行态的菜单只认 `"app"`。
- **别在模块里写 `document.documentElement`。** 见上面样式那节。

## 十一、卡住了怎么办

| 现象 | 大概原因 | 怎么修 |
| --- | --- | --- |
| 整个模块不生效，菜单页面都看不到 | `index.ts` 没有 `export default`，或者被 `filter: true` 过滤了 | 检查入口导出 |
| 菜单不出现 | `owner` 不是 `"app"`，或者菜单还没初始化进库 | 改 owner，重新初始化菜单 |
| 菜单出现了，但外壳没生效 | `match` 里的 code 写错 | 对着 `baseMenu.json` 一个一个核 |
| 外壳生效了，但页面空白 | 外壳里忘了写 `<PageRouteView />` / `<router-view />` | 补上路由出口 |
| 外壳生效了，页面显示但样式全乱 | 你的全局样式没有限定在 `.jl-app-scope` 下 | 加作用域 |
| 我的样式跑到了别的页面 | 同上 | 同上 |
| 控制台提示两个模块都命中 | `priority` 冲突 | 调大自己的，或删掉多余的声明 |
| 改完代码没变化 | Vite 缓存 | `pnpm -F jetlinks-web-core dev:force` |

还搞不定，把控制台那几条 `[Application Shell]` warning 和 `/menu/user-own/tree` 的返回贴出来，基本一眼就能定位。
