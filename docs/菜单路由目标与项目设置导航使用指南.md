# 菜单路由目标与项目设置导航使用指南

## 概述

`options.routeTarget` 用于将已经通过模块过滤和权限过滤的菜单节点，重挂载到指定的目标路由下。它适合下面这类场景：

- 页面仍需生成动态路由，但不应继续出现在原 SideMenu 分组中。
- 多个业务模块的菜单需要统一进入“设置”等二级导航域。
- 来源菜单的 `code` 可能调整，布局层不应维护一组固定 code。

项目端设置导航已经采用这一机制：各 owning module 只声明目标路由 name，`jetlinks-web-core` 根据权限过滤后的目标 children 渲染 Header 设置入口和顶部 Tabs。

## 前置条件

接入前确认以下事实：

1. 当前菜单树中存在一个稳定且唯一的目标路由 name。
2. 来源菜单已经具备可生成的页面路由和组件映射。
3. 来源菜单能够通过当前模块过滤、应用 Scope 和用户权限过滤。
4. `routeTarget` 填写的是目标路由 name，不是目标 URL。

## 快速上手

### 1. 声明隐藏的目标菜单

目标菜单负责承载二级页面。`show: false` 只让它不出现在 SideMenu 中，不会阻止动态路由生成。

```json
{
  "code": "project/Settings",
  "name": "设置",
  "url": "/settings",
  "options": {
    "routeName": "midhub/settings",
    "show": false
  }
}
```

目标路由通常只需要由壳层 owning module 声明一次。项目端使用的稳定目标路由 name 为 `midhub/settings`。

### 2. 将来源菜单挂入目标路由

在来源菜单自己的 `baseMenu.json` 中声明 `routeTarget`：

```json
{
  "code": "system/User",
  "name": "用户管理",
  "url": "/system/user",
  "sortIndex": 3,
  "options": {
    "routeTarget": "midhub/settings"
  }
}
```

不需要在 `ProjectLayoutPage.vue` 或布局 Hook 中追加来源菜单 code。后续即使 `system/User` 改名，只要新菜单仍声明同一个 `routeTarget`，它就会继续进入设置导航。

### 3. 保持页面组件映射有效

`routeTarget` 只改变菜单树中的父子关系，不负责创建页面组件映射。来源 `code` 调整后，仍需同步核对所属模块的 `getAsyncRoutesMap()`、`getExtraRoutesMap()` 或 `componentCode` 映射。

例如 `modules/project-side-ui/index.ts` 根据 `views/**/index.vue` 生成 `system/<view-path>` 组件 key。若菜单 code 与该 key 不一致，动态路由仍可能存在，但页面组件无法正确解析。

## 执行时机与数据流

菜单装配顺序如下：

1. 请求当前用户菜单。
2. 执行模块菜单过滤和权限过滤。
3. `applyMenuRouteTargets()` 根据 `routeTarget` 重挂载菜单。
4. 使用重挂载后的菜单树生成路由、面包屑和菜单缓存。
5. 项目布局从目标菜单的可访问 children 生成设置入口和二级 Tabs。

因此，`routeTarget` 不会绕过模块过滤或用户权限，也不会把无权访问的菜单重新放回导航。

## 配置契约

| 配置 | 所属节点 | 作用 |
| --- | --- | --- |
| `options.routeName` | 目标菜单 | 声明稳定的目标路由 name，推荐显式配置。 |
| `options.show: false` | 目标菜单 | 隐藏 SideMenu 入口，但保留动态路由。 |
| `options.routeTarget` | 来源菜单 | 指向目标路由 name，并在路由生成前移动到目标 children。 |
| `sortIndex` | 来源菜单 | 控制同一目标下的二级菜单顺序；相同时保持原菜单顺序。 |

目标匹配依次使用菜单的 `options.routeName`、顶层 `meta.routeName` 和 `code`。业务配置应优先使用显式、稳定且唯一的 `options.routeName`，避免来源 `code` 调整影响目标识别。

重挂载时保留来源菜单自身的 name、URL、route name、图标、权限声明、按钮配置和 children；只改变它在克隆菜单树中的父节点。输入菜单树不会被原地修改。

## 项目设置导航示例

当前设置域由三个业务模块共同提供菜单：

| owning module | 菜单 code | `sortIndex` | 设置页签 |
| --- | --- | ---: | --- |
| `project-side-ui` | `system/ProjectConfig` | 0 | 概览 |
| `project-side-ui` | `system/ProjectUsage` | 1 | 配置与用量 |
| `jetlinks-space-ui` | `space/AreaManagement` | 2 | 空间管理 |
| `authentication-manager-ui` | `system/User` | 3 | 用户管理 |
| `authentication-manager-ui` | `system/Department` | 4 | 组织管理 |
| `authentication-manager-ui` | `system/Role` | 5 | 角色管理 |

各模块只维护自己的菜单、页面和排序，不需要依赖其他业务模块，也不需要修改 core 中的来源菜单清单。

## 项目布局如何消费目标菜单

项目布局通过以下稳定入口消费设置域：

- `PROJECT_SETTINGS_ROUTE_NAME`：当前为 `midhub/settings`，用于查找目标菜单。
- `useProjectSecondaryMenuExtensions()`：从权限过滤后的菜单缓存解析目标 children，并过滤不存在的路由。
- Header 设置按钮：仅在项目壳层且至少存在一个可访问的设置子项时显示。
- 点击设置按钮：进入第一个可访问的叶子路由。
- 设置域激活时：二级菜单使用顶部 Tabs；普通项目二级菜单继续使用左侧导航。

这套消费逻辑只依赖目标路由 name 和目标 children，不依赖来源菜单 code。

## 异常回退与安全规则

- 找不到目标：来源菜单保留在原位置，并输出 `[Menu Route Target]` 警告。
- 目标是来源自身或来源后代：拒绝重挂载，避免生成循环菜单树。
- 来源已经是目标的直接子项：不重复移动，只参与目标 children 排序。
- 目标 route name 重复：只会采用菜单树中第一个匹配项，因此目标 name 必须保持唯一。
- 来源未通过权限或模块过滤：不会进入目标菜单，也不会显示对应设置页签。

错误配置采用“保留原入口”策略，避免因为目标路由拼写错误导致页面入口直接丢失。

## 兼容旧二级菜单扩展

`useProjectSecondaryMenuExtensions(targetKey, registryTargetKey)` 仍保留基于菜单 code 的组件注册扩展点。项目设置域使用：

```ts
useProjectSecondaryMenuExtensions(
  PROJECT_SETTINGS_ROUTE_NAME,
  PROJECT_SETTINGS_MENU_CODE,
)
```

第一个参数使用目标 route name 读取基础 children；第二个参数继续使用旧的 `project/Settings` code 查找注册扩展。已有运行时扩展无需迁移，新增普通菜单页面应优先使用 `baseMenu.json` 的 `routeTarget`。

## 常见问题

### 设置按钮没有显示

依次检查：

1. 当前是否使用项目壳层。
2. `midhub/settings` 目标菜单是否仍在权限过滤后的菜单缓存中。
3. 目标下是否至少有一个可访问子菜单。
4. 子菜单对应的动态路由是否已经注册，`router.hasRoute(name)` 是否为 `true`。

### 来源菜单仍显示在原 SideMenu 中

检查运行时实际菜单数据中的 `options.routeTarget`，不要只检查本地模板；再确认填写的是 `midhub/settings` 而不是 `/settings`。目标不存在或形成循环时，core 会按安全策略保留来源菜单原位置。

### 设置 Tab 存在，但进入后页面为空

`routeTarget` 已经完成菜单重挂载，但页面组件映射可能缺失。检查所属模块 `index.ts` 中的 `getAsyncRoutesMap()`、视图目录生成的 key，以及菜单的 `code` 或 `componentCode` 是否一致。

### 调整 `sortIndex` 后顺序没有变化

确认修改的是重挂载来源节点自身的 `sortIndex`。没有配置或值不是有限数字的节点会排在已配置节点之后；相同 `sortIndex` 按原菜单顺序保持稳定。

## 验证

运行 core 布局与菜单定向测试：

```bash
pnpm -F jetlinks-web-core test:layout
```

该测试覆盖跨父级重挂载、来源 code 改名、排序、缺失目标回退和循环保护。接入新模块后还应在登录态浏览器中确认：

1. 来源菜单不再出现在普通 SideMenu。
2. Header 设置按钮仅对有权限的用户显示。
3. 设置 Tabs 的名称、顺序、激活态和跳转正确。
4. 页面内按钮权限、详情路由和面包屑行为符合原菜单配置。
