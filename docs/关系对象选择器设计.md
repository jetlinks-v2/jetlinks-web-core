# 关系对象选择器设计

状态：已授权实施单列渐进选择组件、独立验证页及真实数据试查；本轮不接入业务。

## 1. 结论与范围

在 web-core 提供通用 `RelationSelector`，让用户配置“从哪个对象出发，沿哪些关系，找到什么对象”。推荐采用单列逐级选择：选到所需类型就完成，经过中间对象时原位进入下一层。多层正反向路径由组件记录，不要求用户操作路径编辑器。

组件输出沿用后端 `VariableObjectSpec`：静态起点对应 `ObjectSpec`，动态起点使用既有 `objectSource`。不另建关系表达式或图查询 DSL。场景联动提供触发对象和期望结果类型；组件不识别设备触发器、通知渠道、人员联系方式或排班业务。

第一版配置一条有限路径。多条路径的并集、多起点批处理、属性过滤、自动递归闭包与通知发送不进入组件职责。

## 2. 当前实现依据

| 现有能力 | 事实与设计影响 |
| --- | --- |
| core `things/relation/ObjectSpec.java` | `objectType`、`objectId` 和 `related` 描述静态起点与关系链。 |
| core `things/relation/RelationSpec.java` | `objectType`、`relation`、`options`、`next` 已支持多层路径；反向保存在 `options.reverse`。 |
| components `relation/utils/VariableObjectSpec.java` | 用 `objectSource` 支持固定值和上游变量作为对象 ID 来源。 |
| components `relation/utils/VariableSource.java` | `source=relation` 包装关系描述，运行时返回找到的对象 ID；属性提取仍由原调用方配置。 |
| 规则前端 `views/Scene/Save/action/Notify/variableItem/User.vue` | 已输出上述协议，但将起点写死为 device、变量写死为 `scene.deviceId`，且只配置一跳到 user。 |
| 关系控制器 | 已有类型目录、关系定义、对象查询与解析入口；web-core 可以依赖基础关系 API，无需依赖 ontology-ui。 |
| web-core | 已有模块资源注册、对象类型图标、滚动列表等能力。复用现有公共导出与模块注册，不新建注册中心。 |

关系是配置时的类型路径，找到的对象是执行时的数据。保存路径后设备更换负责人，下一次执行应找到新的负责人，而不是继续使用配置时预览的人员 ID。

## 3. 推荐交互

![关系选择交互示意](images/relation-selector.svg)

业务任务：在场景动作等已有配置表单中，选择一条可读、可修改的动态对象路径。

本轮根据“更精简的渐进式交互”反馈，改为一个普通选择框和一个单列浮层。取消左右双栏、独立路径编辑区和“使用此关系”按钮。

未配置时只显示：

```text
接收人
[ 选择与触发设备关联的人员                              ▾ ]
```

打开后，先给用户能立即选完的选项。图标表示目标对象类型，右侧小字辅助说明，只有还需继续选择的行展示右箭头。

```text
┌ 触发设备 ──────────────────────┐
│ [人员图标] 负责人          人员 │  点击即完成
│ [人员图标] 创建人          人员 │
│ ────────────────────────────── │
│ [组织图标] 所属组织      组织 › │  点击原位进入下一层
│ [分组图标] 所属分组      分组 › │
└────────────────────────────────┘

选择「所属组织」后，同一个浮层变为：

┌ ‹ 触发设备 / 所属组织 ──────────┐
│ [人员图标] 负责人          人员 │  点击即完成
│ [人员图标] 成员            人员 │
│ ────────────────────────────── │
│ [组织图标] 上级组织      组织 › │
└────────────────────────────────┘

完成后浮层收起：

接收人
[ 触发设备 › 所属组织 › 负责人                          ▾ ]
```

这相当于“触发设备所属组织的负责人”。真实组件保留目录原名，以分隔符串联；不通过替换“所属”等词生成自然语言，避免不同关系、语言下的歧义。

最常用的一跳选择只需要“打开 → 点负责人”；两跳只多选一次组织。层数增加也始终只显示一个浮层，不横向生长级联列，不叠加抽屉。

默认操作：

1. 场景联动传入“触发设备”这个起点；只有一个起点时直接展示，不再要求重复选设备类型。
2. 浮层只列当前类型的关系。能直接到达期望类型的行在前，其他类型在后；选“负责人”直接提交完整值并收起，选“所属组织”进入组织关系列表。
3. 进入下一层后，顶部仅增加短面包屑，列表在固定宽度内替换。点击返回或面包屑可回到前面任一层，滚动位置和搜索词按层保留。
4. 选到期望类型前只改草稿；选到时一次提交。点外部或按 Esc 关闭，放弃未完成的换选，保留原配置，不再增加“应用 / 取消”按钮。
5. 重开已选值时，回到最后一层并勾选当前关系；面包屑可直接回到中间层重新选择。

少用能力按需出现：

- 多个起点：浮层顶部的起点可下拉切换；单起点不显示该控件。
- 搜索：由标题旁的搜索图标展开，只搜索当前层关系名、目标类型；换层后收起，返回时恢复该层搜索。首屏不固定放搜索框。
- 继续多跳：已选值重开后，底部提供弱化入口“从「负责人」继续查找”。它从当前终点进入下一层，适用于人员 → 岗位 → 人员等路径；选到合法终点才替换原值。默认选取流程不增加确认步骤。
- 清空：复用统一选择控件的清空入口，不在每段增加删除按钮。
- 直接用起点：起点符合要求时，首行提供“触发人员本身”等明确选项，对应零跳。
- 未限定终点类型：任一关系行均可完成选择；继续多跳使用同一个“继续查找”入口，不改变控件含义。

编辑规则：

- 修改起点但类型相同，保留关系路径；起点类型变化时清除不再适用的路径。
- 返回上一层只浏览，不立即截断原配置。选择新分支后替换其后草稿，完成后一次提交；不暗中保留用户未重新选择的尾段。
- 长路径的面包屑保留起点与当前层，中间折叠为可展开菜单；候选区高度稳定，异步加载不撑开表单。
- 允许类型重复，如设备 → 人员 → 设备。类型重复不能证明实例闭环，不能仅凭类型重复禁用关系或标成“循环错误”。
- 已保存关系失效时，在摘要旁提示需要重新选择；目录请求失败保留原值并支持重试，不将失败当成空目录或自动清空配置。
- 运行结果可能为空或多人，但配置界面只选择关系描述，不在关系行展示未经真实查询的人员数量。

方案档案：

| 字段 | 约定 |
| --- | --- |
| 方案 | 单列原位逐级选择，复用资源选择器的弹层与候选行，不采用双栏路径编辑器。 |
| 信息密度 | 默认只显示一个选择框；浮层只呈现当前位置和当前层关系，建议宽 320–360px、行高 36px、超高滚动。 |
| 筛选 | 当前层搜索按需展开，使用基础搜索输入，不引入 ProSearch 或完整条件编辑器。 |
| 编辑梯度 | 摘要就近展开一个浮层；选合法终点即提交，关闭放弃未完成草稿。 |
| 核心组件 | 复用 web-core 公共选择交互和 `ObjectTypeIcon`，结合 Ant Design Vue 浮层、菜单及搜索；大量候选再复用 `VirtualScroll`。 |
| 状态锚点 | 顶部面包屑表示当前位置，勾选表示已保存的终点关系；文字用中性色，主色用于当前选项和键盘焦点。 |
| 主动作 | 点击关系行：合法终点完成选择，中间类型进入下一层。无独立确认区。 |
| 不借鉴 | 不复制对象工作台画布、自动布局、仪表盘指标卡、绑定操作、关系定义管理或嵌套详情面板。 |
| 备选 | 原双栏适合专门编辑复杂路径，本需求用单字段选择更合适；横向多列级联会随着层数变宽，全量关系图会引入布局操作，均不采用。 |
| 确认方式 | 本次仅输出方案；确认后实施组件及首个调用方接入。 |

## 4. 配置格式

### 4.1 组件值：VariableObjectSpec

下面是动态起点与两跳关系的示例。示例假设目录确实返回 `asset-owner` 与 `manager`；`manager` 仅用于说明负责人关系，不是组件约定的固定 ID。

```json
{
  "objectType": "device",
  "objectSource": {
    "source": "upper",
    "upperKey": "scene.deviceId"
  },
  "related": {
    "objectType": "org",
    "relation": "asset-owner",
    "next": {
      "objectType": "user",
      "relation": "manager"
    }
  }
}
```

约定：

- `objectType` 是起点类型，`related.objectType` 是第一跳的目标类型，逐层 `next.objectType` 是后续目标类型。
- 每段的 `relation` 必须来自当前类型的关系目录。显示名、图标、样例对象及草稿 key 不进入执行配置。
- 从反向一侧导航时仍保存原关系 ID，并在该段写入 `"options": {"reverse": true}`；界面展示反向名称。正向默认省略该选项。
- 静态起点直接使用 `objectType + objectId`；动态起点使用 `objectSource`。不要把 `${scene.deviceId}` 填进 `objectId` 冒充模板解析能力。
- 原协议的 `objectSource.source` 只支持 `fixed` 和 `upper`。上游来源在本版应是单个对象 ID；数组起点由调用方既有批处理处理，不将数组转成一个字符串 ID。
- 起点本身符合期望类型时，允许零跳，例如由触发人员直接作为通知接收人。

### 4.2 通知调用方保留原包装

通知变量仍使用现有 `VariableSource`：

```json
{
  "source": "relation",
  "relation": {
    "objectType": "device",
    "objectSource": {
      "source": "upper",
      "upperKey": "scene.deviceId"
    },
    "related": {
      "objectType": "user",
      "relation": "manager"
    }
  }
}
```

通知模块把组件结果放入 `relation`，并继续维护原 `options`、属性提取和通知变量结构。电话、邮箱、第三方用户映射由通知模块处理；关系选择器只负责找到人员对象。

多条可选路径若确有需求，优先由调用方承载 `VariableObjectSpec[]`，以多行复用同一组件。不要先把 `ObjectSpec` 改成分支图、表达式树或一套新查询语言。

## 5. 组件边界与接入建议

建议的公共输入：

```ts
interface RelationSelectorOrigin {
  key: string
  label: string
  // 只含现有 objectType / objectId / objectSource 的起点描述。
  root: Pick<VariableObjectSpec, 'objectType' | 'objectId' | 'objectSource'>
}

interface RelationSelectorProps {
  value?: VariableObjectSpec
  origins: RelationSelectorOrigin[]
  targetTypes?: string[]
  disabled?: boolean
  readonly?: boolean
}
```

使用示意：

```vue
<RelationSelector
  v-model:value="receiverRelation"
  :origins="triggerObjectOrigins"
  :target-types="['user']"
/>
```

以上是拟议公共契约，并非已导出的组件。`triggerObjectOrigins` 由场景模块从触发器及上游变量元数据生成，web-core 不读取场景私有 store，也不硬编码变量路径。固定对象的选择继续复用所属业务模块已有选择器；宿主把选中的对象作为起点传入，本版不再建立对象选择器注册体系。

职责落点保持四类即可：

| 落点 | 职责 |
| --- | --- |
| `src/components/RelationSelector/` | 摘要、当前层、候选项、逐级导航与终点提交。 |
| 邻近 composable / 纯转换函数 | 段状态、过期请求处理、递归配置与编辑数组之间的无损转换。只按职责拆分，不建立空包装。 |
| web-core 关系 API / service | 读取基础类型和关系目录，规范化方向与显示名；不读取其他 UI 模块私有文件。 |
| 场景/通知等调用方 | 提供起点、限制终点类型，保留原变量包装及发送行为。 |

已有模块中心用于模块资源注册与图标、业务展示能力复用。若后续确需业务专属来源编辑器，再在既有模块中心声明最小契约，不为本组件新建全局注册器、Provider 管理器或依赖 ontology-ui。

## 6. 元数据、权限与运行语义

- 候选主要复用 `GET /relation/types`、`GET /relation/{type}/relations/_all` 及基础类型完整模型接口。按需读取当前段，不为打开选择器加载全量实例或预先遍历整张图。
- 一个候选的身份由当前类型、关系 ID、目标类型与方向共同确定。不能用显示名或仅目标类型作为 key；多个不同关系可以通往同一种类型。
- 名称由目录本地化后显示。`RelationInfo` 当前只暴露 name/reverseName 等字段，实施时需核验其与完整元数据的国际化一致性；优先复用平台已有本地化能力，不在前端拼后端译文 key。
- 选择关系不是修改关系，不提供绑定、解绑或创建关系定义。目录允许配置某种路径，也不代表执行者拥有路径上所有对象的数据权限。
- 路径实际执行继续走基础关系能力，权限由数据提供方按运行时可信上下文执行。前端不模拟资产授权，本体模块不加入此执行链。
- 路径按显式 `next` 有限次执行，不等同于“递归所有后代”。树的递归范围由具备闭包查询能力的来源明确提供，不能将同名父子关系自动解释为闭包。
- 没有关联就返回空结果；查询失败与空结果分别呈现，不能降级成全体用户或默认管理员。
- 路径可能返回多人。通知调用方按对象类型与 ID 识别结果、处理重复接收人；不在选择器里偷偷选择第一个人。单值消费方必须明确处理多结果。
- 配置时只核验来源、关系连续性及终点类型。多层运行的扇出、时限和结果规模由现有执行边界管理，不向 ObjectSpec 随意塞入重试、分页或发送选项。

## 7. 试算建议

允许宿主提供一个明确的样例对象，显式点击“试算”，只读查看一条配置在该对象上找到的结果。结果用业务名称及所属模块图标显示，不把样例 ID 写回动态起点。

试算是可选接入，不成为第一版路径编辑的前置条件。现有 `POST /relation/_parse` 接受已解析起点的 ObjectSpec 并返回流，没有分页/总数契约；不能把它包装成“精确总量 + 无限结果预览”。实施时若复用它，应先确认来源授权和结果边界，缺少有效边界时先不开放真实试算，不新建一套前端关系执行器。

试算只查询，不发送通知。样例未找到人员不证明所有触发设备都找不到；加载失败也不能显示成“0 人”。
