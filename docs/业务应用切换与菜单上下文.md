# 业务应用切换与菜单上下文

## 运行时默认入口按角色归属选择

当前规则：普通项目入口中，有效角色非空且全部属于应用时，进入 `/business-application/me` 返回的第一个真实业务应用；仅项目角色、混合角色、空角色和管理员保留项目默认流程。角色归属通过未携带应用 Scope 的 `/authorize/me` 判断，选择入口后才加载对应菜单；角色归属本身不代表拥有页面权限。显式应用链接、显式项目 Scope 和主动应用切换保持各自的访问意图。

影响范围与 owning module：仅 `runtime-ui/jetlinks-web-core`，任务级别为 M。入口为 `src/views/login/hooks/useLoginSuccess.ts`、`src/views/login/components/SubAccountLogin.vue` 和 `src/router/startup.ts`；分流与失败边界由 `src/router/default-entry.ts`、`src/router/index.ts` 承载，角色查询和缓存由 `src/api/auth.ts`、`src/store/auth.ts` 承载，复用 `src/store/businessApplication.ts` 及现有菜单和应用访问上下文。下文运营端历史范围不代表本节改动范围。

实现链路：

1. 先通过应用列表确认项目路径或裸应用路径的入口身份，再读取当前用户信息；普通项目入口请求 `GET /authorize/me`，显式禁用应用 Scope，读取未按应用裁剪的认证维度。维度 type 兼容字符串及 `{ id }`，排除 `options.ignore === true` 的角色；同一会话合并并缓存角色查询，退出或换账号后清空，旧请求不得回填新会话。
2. 按角色归属识别入口：有效 role 维度的 `options.applicationId` 有值时为应用角色；无值时为非应用角色。仅在有效角色非空且全部为应用角色时自动进入应用；角色为空不满足此条件。存在非应用角色或当前用户为管理员时保留项目默认流程，不据此断言用户已有项目页面权限；不能把租户维度、应用成员关系或数据权限范围直接当作项目角色。
3. 仅应用角色分支使用 `/business-application/me` 获取当前用户可进入的应用，保留接口返回顺序，选择第一个真实业务应用，跳过前端附加的项目切换项。复用既有应用访问上下文和 Scope 写入逻辑，再加载该应用菜单；不先加载项目菜单或两端菜单反推身份，也不按角色顺序另行排序。
4. 应用列表为空、首个应用无菜单或进入失败时反馈对应失败，不静默回退项目入口或自动尝试其他应用；认证接口失败不视为应用身份。登录成功与已有会话访问项目默认入口共用此判断，显式应用访问链接与主动切换保留原行为。

登录上下文：普通登录删除原先通过菜单 `owner` 反推入口的请求；已有项目或应用凭证在就地登录后同步新 token，避免查询角色时仍使用上一账号的凭证。默认跳转保留当前项目路径，应用链接保留原应用及 `applicationScope`。跨项目 `用户名@项目编码` 和独立子账号登录先进入目标项目 URL，再由统一启动流程分流；子账号登录不再无条件进入首个应用。整页应用跳转发起后中止当前项目导航；失败进入 403 时停止默认分流，避免 403 重定向循环。

不做：不修改运营端 `ui/`、后端接口或授权数据、业务页面、应用切换 UI；不新增入口选择页。

边界与风险：只对“有效角色非空且全部为应用角色”自动进入应用。用户直接授权、组织/岗位授权、模板授权等不作为角色归属依据，空角色保留项目默认流程；管理员沿用现有管理员判断。不能因存在 tenant 维度或任意非应用 API 权限就认定有项目页面权限。应用列表顺序由后端返回决定，前端不增加排序或首项不可用时的应用遍历策略。仅应用角色及空有效角色的真实账号已在本地联调；管理员、项目角色、混合角色及多应用返回顺序的真实账号组合仍待环境联调。

## 运营端原有应用切换与菜单上下文

项目与应用运行态前端左上角标题作为业务应用切换入口。可选项来自 `GET /business-application/me`；进入业务应用时，应用运行态的 project storage 会写入 `scope: <applicationId>`，`package.ts` 请求拦截器据此为该应用下所有接口携带 `X-Application-Scope: <applicationId>`。项目本身不写入 `scope`，因此项目接口不携带应用 Scope。租户端启动或刷新时不初始化业务应用上下文，也不为系统配置自动请求业务应用列表或详情；租户应用管理页的显式 CRUD 不在此限制内。

应用选择保存在当前浏览器标签页的 `sessionStorage` 中，应用运行态的接口 Scope 保存在对应 `project_<applicationId>` 的 project storage 中。运行边界统一通过 `src/utils/business-application-runtime.ts` 判断：仅非微应用下的项目路径及其应用入口初始化应用列表；租户根端即使 `VITE_APP_ENVIRONMENT='saas'`，启动时也不会自动请求 `/business-application/me` 或 `/business-application/{id}`，菜单初始化还会显式传入 `false`，避免读取当前标签页遗留的应用 Scope。独立项目端即使 `VITE_APP_ENVIRONMENT=''` 仍会请求 `/business-application/me`。项目运行态在没有显式 `applicationScope` 时默认保留项目菜单；子账号登录成功后会主动查询应用列表，并通过同一套“进入应用”逻辑进入第一个业务应用。若当前账号没有业务应用，则继续走原项目入口逻辑。

应用端 Header 右侧的应用快捷入口同样消费 `src/store/businessApplication.ts`，展开弹层时通过 `refreshApplications()` 重拉 `/business-application/me`。租户端不会挂接这个请求入口。刷新会保留仍然有效的当前应用 Scope；当前应用已删除时才回退到项目入口或首个可用应用，避免列表同步意外改变菜单上下文。

当业务应用列表非空时，下拉中会附加一个项目入口。该入口使用项目菜单请求，不写入 storage scope，用于从业务应用切回项目本身。

## 租户、项目与应用布局分层

目标是在不改变菜单、路由、权限和业务页面结构的前提下，将租户端、项目端、应用端的布局样式收口到三个独立壳层。`src/layout/BasicLayoutPage.vue` 只负责根据当前作用域选择壳层；菜单状态、导航、响应式尺寸、二级菜单和布局级生命周期统一由共享 composable 编排，避免三端复制相同处理逻辑。

布局入口统一由 `useBasicLayoutVariant()` 按运行态选择：`isApplicationRuntime()` 为真时使用 `application`，否则 `isProjectRuntime()` 为真时使用 `project`，其余使用 `tenant`。固定项目部署通过 `VITE_APP_RUNTIME_SCOPE=project` 识别，不要求 URL 携带项目标识。布局组件和共享控制器消费同一个结果，不再读取 `front.layoutVariant` 或标签页应用 Scope 来独立决定入口壳层。运行态按布局创建时的入口确定，存储变化不会触发响应式更新。现有 `front.layout` 继续只表示 `side`、`mix`、`top`，不承担壳层类型语义。

实施入口：

- `src/layout/runtime/layoutVariant.ts`：布局类型定义与配置值规范化。
- `src/layout/hooks/useBasicLayoutVariant.ts`：按应用、项目、租户顺序统一判断入口壳层。
- `src/layout/hooks/useBasicLayoutController.ts`：共享布局状态、菜单和生命周期。
- `src/layout/shells/`：租户、项目、应用三个独立壳层入口及当前共享渲染骨架。
- `src/layout/BasicLayoutPage.vue`：布局分发和共享上下文提供者。

本次只建立分层和样式作用域，三个壳层默认复用当前布局骨架，避免在没有视觉方案时改变用户界面。后续样式差异只在对应壳层作用域内演进，不向业务页面或其他运行态泄漏。

## 应用模板布局变体前端接入计划

目标：前端新增业务应用模板时统一写入扩展字段 `layoutVariant: "application"`；基于模板新增业务应用时，将模板的布局变体复制到应用的 `configuration.layoutVariant`；进入应用端后，`ApplicationLayoutPage.vue` 只读取当前应用详情中的配置并传给共享布局壳层。

影响范围与 owning module：模板新增入口只处理 `ui/modules/authentication-manager-ui/views/application-center/Template/`；业务应用创建和模板数据转换位于同模块的 `views/application-center/ProjectApplication/`；应用详情类型与布局消费位于 `ui/jetlinks-web-core/src/api/application.ts` 和 `src/layout/shells/ApplicationLayoutPage.vue`。不修改 `ui/modules/saas-manager-ui`、`runtime-ui` 或后端。

不做：不新增模板表单项，不修改模板或业务应用后端实体，不让 `ApplicationLayoutPage.vue` 请求模板详情，不调整菜单、权限和系统配置接口，不改变租户端与项目端壳层。现有模板或应用缺少该字段、字段值非法时继续使用 `application`。

实施步骤：先补齐应用管理模块中的模板、应用运行配置和前端展示模型布局字段类型；再让应用管理模块的模板新增入口提交默认扩展字段；随后在业务应用创建编排中从已选模板复制合法的布局变体到 `configuration.layoutVariant`；最后由 `ApplicationLayoutPage.vue` 从业务应用 Store 已加载的当前应用详情中同步派生布局变体。

风险与待确认：该方案只影响通过当前前端创建的新模板和新应用；历史模板、历史应用以及绕过前端直接调用接口创建的数据不会自动补齐字段。应用更新时必须保留已有 `configuration.layoutVariant`，避免编辑名称、语言、时区或域名后覆盖布局配置。

验证方式：本次按用户要求不执行构建、类型检查、测试或页面冒烟；交付时列出待确认的模板创建请求、应用创建请求与应用端布局消费链路，不把未执行项记为已验证。

实现结果：应用管理模块新增模板时写入 `layoutVariant: "application"`；模板列表归一化后保留合法布局值，并在新增业务应用时复制到 `configuration.layoutVariant`。应用更新沿用原有配置展开逻辑保留该快照；`ApplicationLayoutPage.vue` 直接消费业务应用 Store 中的当前应用详情，不发起模板查询。

验证结果：按用户要求未执行构建、类型检查、测试、静态检查或登录态页面冒烟；模板创建请求、应用创建请求和应用端布局切换仍待目标环境确认。

## 项目设置导航与 Header 调整计划

项目端采用“当前项目详情工作区”：普通业务二级菜单保持左侧导航，设置域使用顶部横向 Tabs；项目 Header 右侧复用现有业务应用 Store 提供应用切换入口，并增加权限感知的设置入口。项目端不提供菜单收起按钮，租户端和应用端保持原行为。

设置菜单由 `baseMenu.json` 声明 `options.routeTarget`，不在布局层维护来源菜单 code。项目端直接使用隐藏的 `system` 父菜单作为目标；菜单权限过滤完成后、动态路由生成前，通用菜单装配能力将来源菜单移动到与 `routeTarget` 匹配的目标路由下；来源菜单继续生成原 name/path 和按钮权限，但不再出现在普通 SideMenu。目标不存在、目标循环或目标无效时保留来源菜单原位置，避免配置错误导致入口丢失。

本次目标路由 name 为 `midhub/settings`。`概览`、`配置与用量`、`空间管理`、`用户管理`、`组织管理`、`角色管理` 分别由 owning module 的 `baseMenu.json` 声明目标和排序。项目端只消费目标菜单的权限过滤后 children；个人中心保持独立，通过头像菜单进入。以后来源菜单 code 变化时，无需修改布局代码。

实施入口：

- `src/utils/menu.ts`、`src/store/menu.ts`：`routeTarget` 菜单树重挂载、路由/面包屑/权限生成及安全回退。
- `src/layout/hooks/useProjectSecondaryMenuExtensions.ts`、`useBasicLayoutController.ts`：读取目标 children、设置可见性、激活态和首个可见叶子。
- `src/layout/shells/BasicLayoutShell.vue`、`ProjectLayoutPage.less`：项目 Header 入口、禁用收起、设置态顶部 Tabs 和 scoped 样式。
- `src/layout/components/BusinessApplicationSwitcher.vue`：在不复制 Store 逻辑的前提下支持 Header 呈现模式。
- `../modules/project-side-ui/baseMenu.json`、`../modules/authentication-manager-ui/baseMenu.json`、`../modules/jetlinks-space-ui/baseMenu.json`：声明设置目标、排序和用户可见名称。

业务模块接入步骤、配置契约和排查方式见[菜单路由目标与项目设置导航使用指南](./菜单路由目标与项目设置导航使用指南.md)。

验证覆盖菜单跨父级重挂载、缺失目标回退、循环保护、权限过滤后的目标 children、SideMenu 隐藏、Header 入口可见性、设置默认进入和项目/租户/应用壳层隔离；同时执行相关 JSON 解析、Vue 文件行数检查、定向测试与项目端构建。
