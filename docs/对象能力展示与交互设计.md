# 对象能力展示与交互设计

状态：方案已确认并实施，受控集成测试与实现审查已完成。运行环境和浏览器验收仍待完成，具体证据及限制见第 12 节；本轮不接入流程或指标业务。

配套：[可交互示意](object-capability-prototype.html)。示意使用演示数据，不代表接口已经提供相关业务能力。

## 1. 结论

以“对象身份 + 来源明确的能力 + 有类型的数据 + 显式操作”为共同基础，提供可组合的展示与选择组件。工作台、流程、指标复用这些组件及数据引用，不复用一整个对象工作台。

业务的语义只声明一次：后端 relation 的对象来源及补充 Provider 描述属性、查询、动作、事件和关系；web-core 将其适配到已有 data-capability 运行时。业务前端只为确实需要的表现注册专属组件，普通数值、枚举、对象、列表、参数输入均有默认表达。

延续 `ObjectPresentation`、`moduleRegistry`、`DataCapabilityProvider`、`VariableObjectSpec`，不再建立 ObjectDataProvider、对象专属权限接口或第二套查询/执行框架。

本节保留实施前的源码基线及待补齐项；当前实现以第 12 节和实际源码为准，尚未对运行服务做接口验收。

| 基础输入、局部编辑及详情布局 | `MetadataValueItem`、`Editable`、`KvGrid`、`SectionCard`、`StickyActionBar`、`JlDrawerShell` | 组合复用，按真实 props 做薄适配 |

| 工作台数据读取 | `modules/jetlinks-ontology-ui/hooks/useObjectPresentation.ts` | 将通用部分逐步移到 core，保留图会话编排 |

实施时需补齐以下五处缺口：

1. `ObjectPresentation.fields` 主要面向摘要，单个 `detail.component` 无法细致组合多个来源的能力。工作台注册合并按字段 key 覆盖，同名来源可能互相遮蔽。
2. 默认格式化与请求编排部分仍在 ontology-ui；流程、指标若直接复制，会产生第二套字段及时间解释。
3. data-capability 已支持动态数据源，但没有对称的动态操作目录。不能声称实例动作已能直接适配。
4. relation 已有类型/实例模型、命令及只读命令端点；当前这些 HTTP 端点没有显式 provider 选择参数，也缺少通用属性批量读取端点。Java `ObjectOperations.forProvider()` 已支持来源选择。前端不能仅靠给名称加来源后缀解决实际路由。
5. `CapabilitySchema` 不完整包含物模型的单位、语义角色等信息。执行 Schema 与原语义元数据需并存，不能转换后丢掉原模型。

数据运行时边界按[数据能力注册中心设计](数据能力注册中心设计.md)第 8 节：基础 query/connect、绑定、映射、prepare/confirm/execute 已实现；自动轮询、合并调度、自动重试、批量策略等不能因类型中有字段就承诺支持。

## 3. 本体语义如何落到界面

| 概念 | 用户看到的内容 | 交互边界 |
| --- | --- | --- |
| 对象 resource | 名称、类型、状态和基础事实 | 对象身份只有一份，补充来源不创建新对象 |
| 属性 | 类型明确的值、枚举、单位、说明 | 元数据里有属性不等于允许修改 |
| 观测 observation | 值、观测时间、质量，必要时显示区间 | 查询时间不能充当观测时间；单点不能画出趋势 |
| 事件 event | 某次发生、发生时间、当时数据 | 历史事实保持原值，不能用当前状态改写 |
| 活动 activity | 执行进展、开始/结束、来源返回的状态 | 动作受理与执行完成、效果达成分别呈现 |
| 结果 result | 业务产生的结果及来源 | 不因 HTTP 成功自动推断业务成功 |
| 关系 | 主体、谓词、客体及关系实例属性 | 方向、owner、自定义 relation、权限仍由原事实定义 |

直接消费现有 `semanticTypes`、`semanticRole`、`functionKind`、`presentation.primary/observedAt`。现有字段角色包含 `result`、`observedAt`、`quality`、`status` 等；不另造一套前端“设备数据分类”枚举。

数值类型决定格式与输入控件；语义角色决定它是结果、时间还是状态；业务来源决定状态含义、权限及动作效果。未知语义使用有类型的普通展示，不凭名称猜测。

语义可参考 [WoT Thing Description](https://www.w3.org/TR/wot-thing-description11/) 对属性/动作/事件的区分、[SOSA/SSN](https://www.w3.org/TR/vocab-ssn/) 对观测与结果的区分、[PROV-O](https://www.w3.org/TR/prov-o/) 对实体/活动/来源的区分。这里是概念映射，不要求浏览器把全部内部模型转换成 RDF，也不新建推理引擎。

### 3.1 语义覆盖审查

当前方案覆盖了对象内容展示与操作的主干，还不能视为完整的本体建模规范。下表的“覆盖”指设计是否明确，不表示运行代码已经实现。

还需区分三层：本体描述类型、属性、关系及其含义；关系图承载具体对象与事实；查询、写入和功能执行描述对象对外提供的能力。一个动作按钮不是本体关系，一条图上的路径也不是执行因果。

| 概念 | 当前覆盖程度 | 应补充的消费规则 |
| --- | --- | --- |
| 类型、实例与分类 | 对象身份已明确，类型体系仅部分覆盖 | 类型与实例分别定位；支持来源明确声明的多分类、类型层级。产品归属关系不能自动解释为类继承，多个 Provider 补充字段也不等于子类关系 |
| 稳定词汇与身份 | 已有 type/member/provider 标识，跨词汇映射未约定 | 名称只用于展示，稳定标识参与引用；保留来源命名空间。显示名相同不代表同一属性/关系，同名对象不合并；别名或等价映射只能来自明确声明 |
| 数据属性与对象关系 | 已覆盖 | 文本、数值等字面值走类型渲染；对象引用走对象导航与关系表达。JSON 对象/数组只是数据结构，不能因此推断为有身份的业务对象 |
| 带属性的关系事实 | 权限和角色已覆盖，事实上下文仍不充分 | 主体、谓词、客体之外保留来源提供的角色、有效区间与适用上下文；同一对对象可以存在多个不同绑定事实，不能只按两个端点去重 |
| 关系性质与形状约束 | 方向已有，基数/约束需统一 | 目标类型、一项/多项、必填及可维护性来自明确声明。唯一值、对称、传递和反向谓词均不凭关系名推导；约束不等于授权 |
| 观测、事件、活动与结果 | 主干已覆盖 | 观测关联到哪个对象、哪项属性、何时/何区间及何来源必须可追踪；事件类型与某次事件分开，动作定义与执行实例分开 |
| 时间与适用上下文 | 采样/发生/记录时间已区分，关系有效时间需补充 | 当前关系不自动用于解释历史事件；查询窗口、事实有效期与记录时间分别保留。来源不能提供历史视角时明确说明，不伪造某时刻的关系快照 |
| 来源、证据与推导 | 来源与执行记录已有，直接/推导事实尚未明确 | provider 标识说明能力由谁提供，不能代替某条事实的证据。直接事实、闭包结果、规则推导与计算结果按来源标注；图上可达不证明另一条关系成立 |
| 未知、否定与完整性 | 空值与错误已区分，否定语义需补充 | 未加载、未返回、无权限、部分返回均不能推出“不存在”。只有来源明确保证相应范围完整，或提供明确否定事实时，才能作范围内的否定判断 |
| 模型演进与兼容 | 已有绑定版本与失效处理 | 类型/成员重命名不改稳定标识；移除、类型变化、弃用及等价替换按真实声明提示，不按相似名称自动替换 |

### 3.2 优先补充什么，如何避免扩大实现

**第一步补齐消费规则，复用原有模型与运行时，不增加基础设施。**

1. **身份与语义分开。** 对象保留原稳定身份；成员引用保留来源和标识；对象引用、字面值、记录样本分别呈现。能力成员选择不能仅按展示名或值类型匹配。
2. **关系按事实表达。** 对实例属性使用来源提供的事实身份或查询契约识别；没有稳定事实 ID 时不自行伪造全局边 ID。角色、权限、有效时间放在关系实例上下文，不能变成客体对象自身属性。owner 或自定义 relation 继续沿用原业务含义，不自动传播权限。
3. **结果带适用范围。** 保留来源实际返回的对象、来源、时间窗口、质量及分页/完整性信息；未声明的信息保持未知。只在界面作有依据的说明，不要求所有数据强制实现一套庞大信封结构。
4. **约束只控制交互。** 按来源声明的一项/多项、参数类型及动作可用性选择控件；后端执行仍负责真实约束与授权。来源未声明可写就不生成写入入口，不靠布尔类型或属性名称判断。
5. **动作与效果分开。** 沿用原方案的“受理 → 执行结果 → 可验证效果”；来源没有后续状态或效果证据时，只显示已知阶段，不为展示增加通用状态机、轮询器或前置/后置条件引擎。

**来源有明确元数据时再启用：** 多分类/类型层级、逆关系、关系有效期、闭包/推导来源、弃用提示。前端接收并保留已有元数据；缺失时不能为填满界面自行补推导结果。此处列明兼容原则，不把这些后端声明全部加入首期必做范围。

**暂不建设：** OWL 推理器、sameAs 自动合并、前端传递闭包、全量 SHACL 校验、自动单位换算、可信度评分或通用业务规则引擎。若后续确有跨词汇交换或形式约束需求，再分别选择标准映射；不以“符合本体论”为由一次性引入。

概念参考补充：[RDF 1.1 Concepts](https://www.w3.org/TR/rdf11-concepts/) 用于区分稳定标识、字面值与关系事实；[OWL 2 Primer](https://www.w3.org/TR/owl2-primer/) 用于理解类型、实例及关系性质；[SHACL](https://www.w3.org/TR/shacl/) 用于理解形状约束与验证的独立职责。这里采用其概念边界，不宣称当前系统已实现这些标准，也不把有限接口结果等同于完整知识库。

### 3.3 界面及复用的具体含义

- **图中组织绑定：** 同一设备与同一组织可同时有 owner 和自定义协同关系；以实际关系事实区分，不合并成一个无差别“已关联”。关系来源提供有效区间时，在关系详情中显示，卡片摘要保持简洁。
- **“张三管理的设备是否存在问题”：** 先按声明的关系范围找到设备，再按声明的观测读取状态。只查到一页或部分对象时显示“已检查当前返回的对象”；某个来源不可读时显示未完成，不能输出“均正常”。
- **流程取数：** 从路径取得多个终点时保留集合身份及来源；不隐式取首项、跨来源合并，或因某些对象未返回数据就把它们解释为否定结果。
- **指标输入：** 单位相同不表示观测属性相同；例如目标温度与实测温度不能因同为 ℃ 就互换。字段选择同时呈现业务含义、类型、单位和时间语义，计算仍使用原值。
- **历史记录：** 某次告警的发生对象和当时数据属于该次事实；当前负责人/组织只表示当前关系，除非来源明确提供当时关系，否则不作为历史归属证据。

这些信息按需进入字段提示、详情及结果范围说明；首屏继续保持原方案的紧凑内容区，不新增一排本体术语标签。

## 4. 推荐的交互档案

### 推荐：单页对象总览 + 就近操作

业务任务：在一个页面了解当前对象、查看关键数据并完成常用操作。对普通用户使用具体业务名称，不把本体模型作为导航结构。流程和指标中复用内容及选择部件，其选择任务仍使用宿主自己的轻量承载。

对象浏览：

```text
冷却泵 01   ● 在线                                    [更多操作]
2 项告警待处理                                          [查看]
─────────────────────────────────────────────────────────────
当前数据                         负责人和关联信息
温度             出口压力         张三             负责人
23.6 ℃           0.42 MPa         生产一部          所属组织
14:32:08 采集    14:32:06 采集     维护中心          协作组织
                                 变频循环泵        所属产品
目标温度 26 ℃          [修改]
运行模式 自动          [切换]      [管理关联]
说明 北侧循环管路      [编辑]
[查看更多数据]
─────────────────────────────────────────────────────────────
最近记录                                      [查看全部记录]
14:10  出口压力偏高   处理中
09:23  温度超过范围   已恢复，历时 3 分 41 秒
```

流程 / 指标中的选择：

```text
选择数据
[触发的设备] → [所属组织] → [负责人]                 [继续查找]
[搜索姓名、当班状态等数据]
  姓名
  当班状态
  排班记录                                 说明按需展开
──────────────────────────────────────────────────────────────
已选：负责人 / 当班状态
用一位人员试试看 [选择人员]                      [使用当班状态]
```

- 信息密度：首屏只呈现 2–4 项关注数据、少量基础信息和当前关联；最近记录在同页下方。数据较多时在原区块展开、搜索或分页，不依次铺满整页，也不强求一屏容纳全部内容。
- 编辑梯度：单字段就地编辑；有依赖的少量参数就近展开；复杂业务维护使用来源组件；仅跨对象、长流程操作才进入独立业务页面。
- 核心组件：`KvGrid`、`Editable`、`SectionCard`、`MetadataValueItem`、`RelationSelector`；必要时使用 `StickyActionBar` 和 `JlDrawerShell`，不叠加抽屉。
- 状态锚点：当前对象、展开区块、输入草稿、时间窗口与滚动位置。请求的来源身份保留在内部；对象切换不挪动图布局，旧请求失效。
- 主动作位置：字段右侧、区块标题或局部编辑区底部。与当前字段相关的修改不再在页头重复出现；页头只保留对象级操作。“使用当班状态”等选择动作固定在选择器底部。
- 不借鉴清单：概览/数据/功能/记录四套互斥页签、全字段表单、四个装饰指标卡、给所有值加彩色背景、来源名称铺满首屏、仅 hover 才能发现的关键操作、把关系维护再复制进记录列表。

关系图中的节点只呈现身份和已选摘要。单页总览可作为独立页面，也可作为图旁的同一内容区：宽容器两列、窄容器一列，不复制整个平台壳。关联区只投影当前关系摘要，管理关联仍进入原统一维护承载；不新增一套绑定界面，也不把完整多层关系图强塞进总览。

### 4.1 面向用户的表达规则

本体语义用于保证数据正确、决定展示和交互，不作为普通用户必须学习的概念。技术说明留在本文；产品界面只展示当前任务需要的信息。

| 原示意中不够自然的表达 | 用户侧表达 / 交互 |
| --- | --- |
| 对象内容与能力、对象范围 | 使用对象的业务名称；选择时说“从哪个设备开始”或宿主提供的同类文案 |
| 查询能力、动作、执行功能 | 数据使用业务名称；操作使用“读取最新值”“修改目标温度”等具体动词 |
| 枚举、标量、结构、结果模型 | 不常驻显示。用具体值、单位、可展开明细和必要图标表达；图标提示也不放程序类型 |
| provider、命名空间、能力 ID、owner | 不进入正文、tooltip 或错误提示。确需解释差异时显示来源的业务名称；关系使用来源声明的“所属组织”等显示名 |
| 保存数据引用、解析关系路径 | 用户只需知道“之后会自动使用触发设备的数据”；具体保存格式不展示 |
| 来源拒绝、部分返回、观测完整性 | 分别表达“当前账号无法查看”“已查看 20 台，仍有未检查设备”等有依据的业务说明 |
| 请求已受理、结果证据 | 按真实阶段表达“已发送，等待设备更新”或“已保存”；不能为了易懂把待生效说成已生效 |

具体场景的名称由业务声明或宿主文案提供，不在 core 中按 device/user/owner 等 ID 编写翻译分支。未知的自定义关系继续使用来源声明的可读名称，不能猜成“所属”或“管理”。

可读性分三层：

1. **默认看到：** 名称、业务状态、关注值、时间、当前可用操作。风险或未完成的说明紧邻当前结果，不藏进 tooltip。
2. **需要时展开：** 更多字段、历史记录、关联对象和业务来源名称。用户做比较或定位差异时才显示必要说明。
3. **留在实现内部：** Provider、Schema、semanticRole、模型版本、原始命令与组件标识；普通用户的“详细信息”也不直接输出这些字段。运维排障沿用原有入口，不在本组件另造技术模式。

### 4.2 单页中的连贯操作

- 查看数据、修改目标值、切换运行模式都留在当前对象。编辑展开在对应行下方，取消后保持滚动和关系图位置。
- “更多操作”在页头下方就地列出可用操作。选中后只展开该操作的必要输入；不再跳到“功能”页签，也不叠加抽屉。
- “查看更多数据”在当前数据区展开查找；“查看全部记录”在记录区展开筛选和分页。数据量大时保留有界结果，收起后恢复紧凑状态。
- 点击告警提示定位到同页对应记录；点进具体记录才按需展开详情。关联信息与业务记录分区，避免重复展示。
- 图旁窄内容区按数据、基础信息、关联、记录顺序单列。大量分区可用滚动定位；它只定位同页内容，不成为新的互斥页签。
- 无业务来源内容的区块不出现；空值、失败和权限不足用具体业务对象及动作说明，不把内部异常原文带到界面。

### 不同宿主的承载

独立对象页使用两列总览；图旁内容区使用同一总览的单列布局。它们共用内容与交互，区别只在可用宽度和区块密度。流程/指标选择器只嵌入当前选择所需的部件，不展示整份总览。

不再将“完整详情页 + 多页签”作为默认备选。遇到超出轻量编辑范围的业务管理，使用来源明确提供的业务入口。

### 4.3 仪表盘式总览：默认好用，按需自定义

可以将同一总览作为用户可选内容、拖动、调整大小并保存的仪表盘。推荐“默认总览 + 我的页面”，首次进入仍有完整、合理的默认内容，无需先搭建才能使用。

普通用户看到的入口是“自定义页面”，不使用“组件编排”“数据源绑定”“模型配置”等名称。

```text
冷却泵 01   ● 在线                             [自定义页面]
2 项告警待处理                                      [查看]
─────────────────────────────────────────────────────────
┌ 当前数据 ──────────────────┐ ┌ 负责人和关联信息 ─────┐
│ 温度 23.6 ℃  压力 0.42 MPa │ │ 张三          负责人 │
│ 目标温度 26 ℃      [修改]   │ │ 生产一部    所属组织 │
└────────────────────────────┘ └──────────────────────┘
┌ 最近记录 ───────────────────────────────────────────┐
│ 14:10  出口压力偏高  待处理                         │
└─────────────────────────────────────────────────────┘

点击“自定义页面”后：
我的页面                 [添加内容] [恢复默认] [取消] [保存]
┌ ⠿ 当前数据                      [选择数据] [移除] ┐
│  保留上次读到的值；拖动标题，右下角调整大小          ◢│
└─────────────────────────────────────────────────────┘
```

**正常查看与调整页面分开。** 正常查看时保留原有的就地修改和功能操作，不显示拖动控件；进入自定义后才显示拖动柄、尺寸调整和移除。拖动只从标题柄开始，输入框、链接、图表和业务按钮不触发拖拽。调整页面期间不执行对象动作，保存布局也不提交设备参数或关系更改。

用户可以选择的内容按任务组织：

| 用户看到的内容 | 选择方式 | 展示方式 |
| --- | --- | --- |
| 当前数据 | 搜索并选择温度、压力、运行状态等实际数据名称 | 可选几项组成一组，也可把某项单独放大 |
| 基本信息 | 选择需要显示的已有字段 | 紧凑键值，就地编辑仍由来源动作提供 |
| 关联信息 | 选择负责人、所属组织等实际关联名称 | 名称、必要角色和关系属性，更多对象有界查看 |
| 最近记录 | 选择告警、排班、工单等来源实际提供的记录 | 保留既有记录表现、时间范围和分页 |
| 常用操作 | 选择实际可执行的动作名称 | 显式点击后输入并执行，不因加入页面而自动执行 |

该表是通用分类，具体对象只出现它确实拥有的内容。排班、工单等缺少实际来源时不作为占位入口。“趋势”只在有真实历史查询时可选，不把一个数值组件自动变成趋势图。

**添加内容继续使用渐进选择。** 点击“添加内容”后就近展开内容列表，搜索业务名称；选择数据后再按需选择字段和表现。默认显示适合的样式，仅提供少量有效选择，如“紧凑数值 / 数据组 / 历史曲线”；不开放无依据的任意图表、颜色、CSS 或脚本配置。批量选择字段不必为每个字段创建一张重复外框卡片。

**保存默认只影响自己和当前对象。** 第一阶段支持当前对象的多个个人视图，“保存”更新当前视图，“另存为”产生独立视图，不修改共享视图、对象数据或其他人的页面。内容绑定到“当前查看的对象”，不将预览对象或当时读到的数值固定进组件。刷新及再次打开恢复选定的默认视图，规则见第 4.5 节。

“应用到同类对象”和团队共享模板暂列后续能力：只有来源提供可判断适用性的模型范围后，才允许显式设为同类默认；不能因为同为 device 就假设都有温度。共享模板还涉及独立的维护权限，不混入个人“保存”。用户与租户隔离沿用现有账号配置体系，不新建一套授权。

配置优先级保持简单：显式选择的可访问视图 → 当前用户为此对象选择的默认视图 → 来源/业务提供的默认总览。多个视图之间不叠加覆盖。“恢复默认内容”先形成草稿，保存后生效；取消恢复进入编辑前的完整快照。暂不新增多层个人/团队/角色/继承覆盖算法。

对象名称和必要的操作结果/失败提示保留在固定头部，不允许因为删除卡片丢失当前对象身份或错误反馈。数据区可以按个人偏好移除，不把某种业务（例如告警）硬编码为所有对象必有的固定卡片。

布局采用吸附网格，卡片有合理的最小尺寸；数据更新不重新排序卡片，不因记录条数增加而挤动其他区块。窄屏按已有顺序转为单列，不将窄屏临时排版覆盖保存的桌面位置。拖动之外提供移动顺序的可访问操作，触屏与键盘也能调整。

### 4.4 复用现有仪表盘，保存完整页面

本轮已核对 core 的以下实现：

| 已有实现 | 可直接复用的职责 | 本场景仍需补齐的连接 |
| --- | --- | --- |
| `src/components/DashBoardCanvas/index.ts`、`DashBoardCanvas.vue` | 公开按需入口；注入 catalog；编辑、布局和预览模式 | 由总览宿主提供本对象可选内容，不导入整个可视化项目或设计器 |
| `components/GridCanvas.vue`、`composables/useDashboardState.ts` | 网格拖动、缩放、增删、布局及配置更新 | 接到个人页面草稿，保存/取消由宿主控制 |
| `types.ts` 的 `DashboardValue / DashboardCatalog` | 序列化画布与组件实例；运行组件定义独立注入 | 每个对象内容组件的配置使用已有数据/动作绑定，不再定义一份布局结构 |
| `utils/layoutStorage.ts` | 浏览器本地坐标恢复与旧 key 迁移 | 不能代替完整个人配置的服务端保存和跨设备恢复 |
| `ObjectPresentation`、已有数据能力运行时 | 来源表现、语义和实际读取/执行 | 薄适配成当前对象的 DashboardCatalog，不增加第二套业务注册中心 |

`DashBoardCanvas` 与 `components/Dashboard` 展示组件族是不同入口；此处复用前者。真实代码已将画布、catalog 与可视化业务 store 解耦，因此无需让 core 或本体依赖 visualization-manager-ui。

**内容适配保持少量通用类型。** 数据展示、关联摘要、业务记录、操作区复用本方案组件；用配置保存具体成员及绑定。不能为“每一种对象 × 每一项属性”注册一种新仪表盘组件。业务专属表现继续由原 ObjectPresentation 提供，确需专属配置时复用原编辑器。

**布局保存与业务定义分开。** 完整个人页面沿用 `DashboardValue`：组件列表、稳定实例 ID、可见性、尺寸/位置及组件需要的持久绑定。布局坐标不进入本体事实，也不创建业务关系。已有关注配置和归属并集提供默认内容及候选；用户隐藏某项仅改变自己的展示，不删除来源关注配置或修改共享本体视图。

服务端保存由宿主 service 负责，画布组件仍只接收值和输出变更。原 `/user/settings/...` 适合一般个人偏好，但本场景还要求对象删除后清理所有用户的视图，因此保存资源必须能按对象引用检索，不能只把对象引用藏在 content 中；具体存储边界见第 4.5、4.6 节。不能复用首页选择或主题设置的业务 key，也不能直接声称当前已实现跨设备保存。

**明确的草稿边界。** 进入编辑复制已保存配置；调整时不改服务器配置，也不写正式的浏览器布局 key。现有画布在提供 storageKey 时会随布局变化写 localStorage，因此编辑草稿不传正式 key，避免取消后仍恢复被放弃的布局。服务端确认成功后更新已保存快照；保存失败保留草稿并允许重试，不先提示成功。

编辑时复用 previewMode 和已有已授权快照，不触发业务写入；来源目录及必要候选搜索仍可按需读取。退出编辑重新按原能力刷新，不把编辑快照当成最新数据。正常浏览按现有查询粒度及可见内容读取，复用同请求共享；不为每张卡片加一个独立轮询器，也不为隐藏一个字段重写共享关注计划。

这部分仍为待确认设计。当前 HTML 示意只包含单页总览及原位展开，尚未实现添加卡片、拖动、缩放或保存；不把示意原生 HTML 扩成第二个网格引擎。下一步应以真实 DashBoardCanvas 做隔离接入验证，再更新交互示意的验收结论。

### 4.5 保存模型：一个对象可以有多个视图

`objectType + objectId` 确定视图适用的对象；`id`（即 viewId）确定其中一份视图。前两者是查询范围，不能作为视图的唯一键。

```text
设备 A
  ├─ 视图 v1：运行概览
  ├─ 视图 v2：日常维护
  └─ 视图 v3：告警排查

设备 B
  └─ 视图 v4：运行概览
```

视图是对同一对象的不同呈现，不创建新的业务对象或关系，也不将这些视图全部加入一个读取计划。一次只激活用户当前选中的视图。

拟议逻辑结构如下；不是当前已存在的实体或接口：

```ts
interface ObjectView {
  id: string                 // 视图唯一 ID；创建/另存为时生成。
  objectType: string         // 当前对象类型。
  objectId: string           // 当前对象 ID；首期必填。
  name: string               // 用户看到的视图名称。
  view: DashboardValue       // 原画布配置，含组件配置及原数据/动作绑定。
}
```

例如，同一账号下的 `{ id: 'v1', objectType: 'device', objectId: 'A', name: '运行概览' }` 和 `{ id: 'v2', objectType: 'device', objectId: 'A', name: '日常维护' }` 是两份独立配置。名称可以重名，不用名称充当标识，也不增加名称唯一性校验。创建用户、租户/项目作用域与存储元信息沿用宿主原机制，由服务端确定，不信任客户端传入的 userId。

**存储使用带对象引用的轻量视图资源。** 删除清理要求已经超出直接复用个人设置接口的边界：当前 `UserSettingEntity` 只有 userId/type/key 与字符串 content，控制器只操作当前账号，没有显式的对象引用或按对象清理能力。因此调整此前“首选直接复用用户设置”的建议，使用独立的 ObjectView 配置资源；仍是一条记录一份视图，不引入模板继承、发布版本或视图权限引擎。

当前对象工作台由 `ontology-manager` 承载该资源及其默认引用；两者是个人呈现配置，与原关注模型分开。持久化补充服务端确定的 userId 和实际部署使用的租户/项目作用域，并为“作用域 + objectType + objectId”及个人列表查询建立普通索引，不能将对象引用设为唯一约束。默认引用由同一服务维护、同一对象范围清理；不为此给通用用户设置增加按 JSON 内容扫描或模拟其他用户的删除入口。web-core 通过宿主注入的保存适配调用，既不硬编码本体接口，也不依赖本体 UI；其他宿主可以复用组件而选择自己的存储。

**不直接复用 OntologyModelEntity。** 当前代码中的 `ownerType/ownerId` 表示关注配置归属，`ObjectFocusService` 会把当前对象及其归属对象的有效配置取并集；其 `draftDefinition`、发布版本和授权也服务于可执行业务视图。把多个个人仪表盘直接写成这些对象关注模型，可能导致未选中的视图一起参与读取，并让布局保存承担无关的发布流程。保留原关注配置作为默认内容来源，个人 ObjectView 仅保存选择与呈现；不扩充一个用途枚举来混用两套生命周期。

**默认视图是个人偏好中的一个引用。** 另存 `defaultViewId`，作用域为“当前用户 + 当前项目/租户 + objectType + objectId”。不在每条视图上保存 `isDefault`，避免多条同时为默认。首期不再同时保存一套“最后访问视图”指针；页面当前选择可通过已有路由查询携带 viewId。

进入对象时依次选择：

1. 路由明确指定且当前账号可访问、所属对象匹配的 viewId。
2. 当前用户为该对象保存的 defaultViewId。
3. 来源/业务提供的默认总览，作为未持久化的内置视图。

显式路由指向不可访问或不匹配的视图时说明“此视图暂不可用”，允许回到默认总览，不能静默展示另一对象的配置。个人默认引用因删除或失权失效时回到默认总览；暂时读取失败则提示重试，不当作已删除并清空偏好。不逐个查询其他对象寻找替代视图。

用户侧保持一个页面：

```text
冷却泵 01   [运行概览 ▾]                         [自定义页面]
            运行概览  默认
            日常维护
            告警排查
            ──────────
            新建视图

编辑当前视图：                             [取消] [另存为] [保存]
视图菜单按需提供：重命名 · 设为默认 · 删除
```

| 操作 | 保存规则 |
| --- | --- |
| 保存 | 已有视图保持 id/objectType/objectId，仅更新当前视图内容和名称；不覆盖同对象的其他视图 |
| 首次保存 / 新建视图 | 产生新 id 并保存当前对象配置；名称就近输入，不要求用户填写对象类型或 ID |
| 另存为 | 产生新 id，复制当前草稿内容；原视图保持原样，成功后切换到新视图 |
| 设为默认 | 仅更新当前用户对此对象的 defaultViewId，不改其他用户，也不改视图内容 |
| 重命名 | 保留 id 和默认引用；名称不是权限或路由依据 |
| 删除 | 删除当前用户可维护的该视图；默认引用失效后可安全回退，其他视图不受影响；恢复默认内容不等于删除全部视图 |
| 切换视图 | 有未保存修改时提供保存/放弃/继续编辑；真正切换后清理旧视图的草稿和待确认动作，取消旧读取 |

视图身份与适用对象创建后不通过普通保存修改。跨对象复用应使用之后明确支持的复制/模板能力，先核验目标模型是否适用，不能直接把 objectId 改成另一个对象。当前 view 中的数据绑定仍使用宿主传入的当前对象；归属字段仅定位配置，不作为读取数据的授权凭证。

只保存布局、选择与参数描述，不保存观测值、告警快照、执行结果、用户令牌或可执行组件代码。视图读取和配置修改沿用用户设置的归属边界，视图内数据与操作继续由来源授权；拥有某视图不代表获得该对象的数据权限。

保存仍有草稿边界与失败重试。若原配置存储不提供修订控制，首期明确以最后一次成功保存为准，不宣称支持多人/多端协同编辑；不为个人视图新增锁服务或发布审批流程。

### 4.6 对象删除：统一通知，附属数据由所属模块清理

**推荐提供通用对象生命周期通道，并通过实体注解做薄映射。** 首期只落地当前确有需求的 `object.deleted`，不同时建设完整状态机、删除编排器或级联规则引擎。通用契约和实体适配归 `relation-component`，不归本体后端或前端；对象身份复用 core 的 `ThingId(type, id)`，事件信封和集群传输复用现有基础。以下名称与例子均为拟议接口，当前尚未实现。

本体语义中的“有关系”不能推导出“共同销毁”。删除设备不意味着删除产品、负责人或组织。参考 [PROV-O 的失效概念](https://www.w3.org/TR/prov-o/#invalidation)，对象不再可用与历史事实是否保留是两个问题；数据库清理策略由事实所属模块决定，不根据图上的可达关系自动传播删除。

#### 现有能力与可复用边界

| 当前源码 | 已确认的职责 | 本方案的边界 |
| --- | --- | --- |
| core `things/ThingId.java` | 统一 type/id 身份 | 不再新增另一套对象标识 DTO |
| components `assets-component/.../event/AssetEntityEventPublisher.java` | 本地实体事件、框架快照、提交后转换为 StructuredEvent | 复用这种发布方式及事务工具；对象生命周期不继承资产专属路由和数据投影 |
| components `common-component/.../commons/ClusterEntityEventDispatcher.java` | 提交成功后处理本地监听并广播实体事件，标识远端来源 | 沿用原 EventBus；对象桥接只处理本地事件，不能再从集群实体回放重复发布 |
| components `common-component/.../event/subscription/StructuredEvent.java` | 事件 ID、类型、版本、时间、主体、数据及扩展信息 | 继续使用原信封，不再建立另一套消息格式 |
| authentication-manager `UserSettingEntity`、`UserSettingController` | 当前用户的个人设置 | 不承担没有对象索引的跨用户删除，保存方案已在第 4.5 节调整 |

这些事实来自源码阅读，不等于对象生命周期、可靠投递或视图清理已经通过运行验证。原 `ThingEvent` 表示物模型业务事件，不直接把它改成对象生命周期接口。

#### 业务只声明权威实体

```java
// 拟议注解；仅标在拥有对象身份和生命周期的实体上。
@ObjectEntity(type = "device")
@Table(name = "dev_device_instance")
public class DeviceInstanceEntity extends GenericEntity<String> {
}
```

- 注解只声明实体对应的稳定对象类型；默认 ID 就是实体 `getId()`。不配置任意 SpEL、反射字段路径或 ID 转换脚本。
- 经已有 ORM 元数据扩展点登记映射，并启用对应实体事件；不另做全包扫描或要求实体成为 Spring Bean。注解不自动生成 RelationObjectProvider、属性模型、资产定义或权限规则。
- 注解表示“该行消失即该对象消失”，只能由身份权威来源声明。补充告警数据的 ObjectSupportProvider、辅助明细表、资产绑定表都不因此取得对象删除权。资产类型也不能未经声明直接当作对象类型。
- 转发只使用框架确认已删除的实体快照；不能拿请求传入的 ID 列表、删除前候选或 SQL 影响行数代替实际对象集合。EntityDeletedEvent 与真实 SQL 删除范围在并发下是否一致，列为桥接实施的验收点；不假定所有自定义仓储都具备同一保证。批量删除在原事件边界有界处理，不反查已经删除的对象。
- 逻辑删除、复合对象、外部资源和绕过 ORM 的业务，由权威来源在业务删除成功的链路显式调用同一发布入口，例如 `objectLifecycleEvents.deleted(ThingId.of(type, id))`。发布入口只转换并发布事实，不执行删除。停用、离线、解绑、某个支持模块卸载都不等于对象删除。
- 后续确有消费需求时，再沿用同一通道映射 created/saved/modified；保留框架 saved 的原始含义，不额外查询来猜测它是创建还是修改。

#### 本地映射，提交后发布

```text
权威来源删除对象
  → 本地实体删除事件 / 显式业务通知
  → 提取 ThingId 与可信作用域
  → 事务提交成功后发布 object.deleted
  → 各模块用已有事件订阅入口清理自己的附属数据
```

事务回滚不发布；无事务时只接在实际删除成功之后。注解桥接和显式业务通知二选一，不能为同一次删除同时使用。事件 ID 在来源生成一次，重试沿用；载荷大小与实体字段数量无关，不发送完整实体、用户令牌或认证对象。

信封使用既有 StructuredEvent，最小业务数据为对象引用：

```json
{
  "id": "event-id",
  "type": "object.deleted",
  "version": "1",
  "occurredAt": 1794268800000,
  "subject": "device-id",
  "data": { "object": { "type": "device", "id": "device-id" } }
}
```

来源标识、部署实际使用的租户/项目作用域及追踪信息沿原可信消息元信息传递，不能由客户端提交的字段决定。ThingId 不含租户，跨服务消费必须保留相应作用域，不能只凭两个字符串全局删除。若部署已按独立库/通道隔离，也沿用原隔离机制，不再造一套租户模型。具体元信息编码与订阅分组需要在实施时核对现有传输契约。

实体桥接只监听本地事件并在提交后投递对象通道，不再叠加一套 ClusterEntityEventListener 回放桥。资产公开事件继续承担自己的资产订阅语义，不把对象清理消息直接开放为用户订阅，也不让浏览器直接发布内部生命周期通知。

#### 清理归数据所属模块

| 数据 | 消费者及策略 |
| --- | --- |
| 当前对象的个人视图与默认引用 | 视图存储服务按可信作用域和对象引用，清理所有用户对此对象的配置；不只清理删除操作者的视图 |
| 平台托管关系实例 | relation 的原管理服务清理指向或来自该对象的边，沿用原实体事件及同步机制更新索引/闭包；不删除另一端对象，也不直接绕过原维护链删表 |
| 资产绑定、业务归属、原生业务关系 | 仍由资产和原业务已有删除链路处理；不能因为新增对象事件再做一份重复解绑 |
| 对象关注配置、派生缓存 | 各自所属服务处理直接归属该对象且确属附属配置的数据；不沿归属并集删除产品或祖先组织的配置 |
| 流程、指标等对对象的引用 | 各宿主保留配置并提示引用不可用，是否迁移由用户或业务决定；不删除整份流程或指标 |
| 告警历史、执行记录、审计证据 | 按原业务保留规则处理；对象删除不改写历史主体或事实 |

原业务要求与对象删除同事务完成的约束继续留在原业务服务。提交后的通用事件用于跨模块附属清理，不承诺跨服务原子删除；清理失败也不能把已提交的业务删除描述为回滚。

同一存储的清理通过原集群订阅分组分配处理，避免每个节点重复执行同一库写入；进程内缓存失效则按需通知各节点。消费者必须幂等，失败沿原事件链可观察并使用已有重投能力，不吞异常后报成功。当前已读实现证明了提交时机，尚不足以证明掉电后可靠补发或 exactly-once；实施时先验证现有结构化事件投递能力，不为此预先新增 outbox、消息中间件或任务框架。

视图正常读写仍使用用户身份及来源权限；删除清理是受信任内部事实的系统副作用，不再查询已删除对象来授权，也不新增 Provider#assertAccess、权限包装或第二套权限引擎。保存与删除并发、删除后使用同 ID 重建必须列入验证：不能用迟到的旧事件误删新对象配置；是否允许复用对象 ID 由来源明确，不能凭到达顺序推断。

#### 模块落点与实现边界

- `relation-component`：对象删除事件约定、薄发布入口、实体注解/映射适配，以及本模块托管关系的消费；不收集其他模块的清理实现，不新增 CleanupProvider SPI。
- `common-component`：复用原 StructuredEvent、EventBus 和事务/集群能力；本轮不扩大其依赖，不引入 hsweb-starter。
- core：复用 ThingId，无需为 CRUD 转发引入 Spring 或 hsweb；实体适配只在现有 CRUD/ORM 条件满足时装配。
- 原业务模块：在权威实体上声明注解，或在非标准删除路径显式通知；自己的强一致清理仍归原业务。
- `ontology-manager`：个人视图配置资源及其删除消费，与原关注模型分开；web-core 只接宿主存储适配和不可用状态，不编排后端级联。

本节属于 L 级待确认设计。实施顺序为：先确定事件与作用域契约，再实现最小注解桥接，接入关系/视图两个实际消费者，最后集中验证；不同时引入全量生命周期、任意映射引擎或通用删除编排。

## 5. 最少的组件与扩展点

以下为拟新增能力，名称是设计名，当前没有这些完整公共组件。

| 组件 / 逻辑 | 唯一职责 | 不负责 |
| --- | --- | --- |
| `ObjectOverview` | 将已解析的摘要、数据、关联摘要、操作及记录组合成单页；以既有 DashBoardCanvas 承载可选的个人布局 | 新的网格引擎、请求服务、业务分支、图布局或另一套绑定维护 |
| `ObjectDataView` | 接收模型、结果及状态，按标量/结构/记录显示；compact/detail 两种密度 | 请求、授权、执行、关系解析 |
| `ObjectCapabilityPicker` | 组合既有关系选择器、能力目录和字段选择，返回现有持久绑定 | 创建新图查询语言、执行流程或指标计算 |
| `ObjectOperationPanel` | 根据输入模型/已注册编辑器展示草稿，连接已有 prepare/confirm/execute | 替代业务校验、自动重试、判断设备是否真的生效 |
| `useObjectCapabilities` | 会话内编排目录、绑定、加载和释放，公开状态及意图方法 | 缓存整个平台、保存图布局、硬编码业务端点 |

值单元是 `ObjectDataView` 的内部共享部件；只有出现独立消费需求再公开导出。对象标题继续复用已有摘要/图标规则，不为列表、图卡、详情各建一套对象身份组件。

业务扩展只补在既有 `ObjectPresentation`：

```ts
// 拟议契约，不是当前已导出的接口。
interface ObjectMemberRef {
  providerId: string
  kind: 'property' | 'query' | 'action' | 'event'
  id: string
}

interface ObjectMemberPresentation {
  ref: ObjectMemberRef
  component?: Component // 标准 typed props：原模型、值、状态和对象上下文。
  write?: PersistedOperationBinding // 已有绑定格式；指向来源真实动作。
}

// ObjectPresentation 拟新增 members?: ObjectMemberPresentation[]。
```

设计约束：

- `typeId` 由外层 `ObjectPresentation` 指定；成员以 `providerId + kind + id` 区分。展示名可本地化，不参与路由。
- 模块注册 key 已能提供 UI 贡献者身份；不要再要求业务重复填写 moduleId。来源 providerId 与前端 moduleId 是两种身份，不能互换。
- `component` 接收数据、状态与意图回调，不直接请求 API。其上下文由一个类型对象传递，避免大量独立 props。
- 专用输入直接用现有 `DataSourceDefinition.ui`、`OperationDefinition.ui`、`valueEditors`，不再增加成员 editor 注册中心。
- `write` 只描述操作绑定。草稿通过既有 `ValueBinding` 的 parameter 传入；原值、草稿、提交结果分开。它不把字段变成通用 setter。
- 记录继续用既有 `ObjectPresentation.record`；关系继续用 `objectRelationMaintainers`，不把它们强行塞进字段写入。
- 精确成员声明优先于内置类型展示；重复的精确声明报告冲突并回退为只读默认表现，不能按模块加载顺序选一个执行。
- 旧 `fields/detail/record` 保留。先做消费适配，迁移已验证后再去除重复路径，避免双读和覆盖。

推荐匹配只做“明确成员 → 内置类型”；暂不引入可执行 matcher、优先级打分、继承规则引擎。等多个真实业务出现相同语义组件需求，再增加有限的声明式语义匹配。

## 6. 数据运行与模块职责

```text
后端 relation 对象身份 / 补充来源 / 语义模型 / 原业务读写
                         ↓
web-core relation 适配（模型与执行入口，保留原来源）
                         ↓
既有 data-capability（发现、绑定、读取、操作、释放）
                         ↓
ObjectDataView / ObjectCapabilityPicker / ObjectOperationPanel
                         ↓
对象工作台            流程配置及运行宿主            指标配置
```

- 后端基础 relation 提供真实通用模型与操作投影；本体后端提供上下文、证据和图谱能力。普通对象内容组件不依赖 ontology-ui，也不要求为了查一个属性创建本体视图。
- web-core 的 relation adapter 是已有 `DataCapabilityProvider` 的一种实现，不是新的 Provider SPI。读取动态能力复用 `dynamicSources`。
- 实例动作需要给现有 Provider 增加与 `dynamicSources` 对称的可选动态操作解析入口，复用目录、版本、owner 和生命周期处理。只补 discover/resolve 和 runtime 解析，不重写注册器，也不先扩成任意动态资源框架。
- 前端按来源保留语义元数据；用一个映射函数产生执行用 `CapabilitySchema`。单位、采样时间、枚举原始值等仍从原模型读取，不散落在多个业务格式化函数里。
- 业务已有独立数据能力可以继续存在。只有确实声明“这是哪个对象的哪项能力”才能出现在对象目录，不能把整个模块所有报表自动挂到对象上。
- 业务模块负责复杂展示、输入交互及既有业务读写；本体模块负责图关系、关注视图和证据组合；流程负责变量、控制流及执行，指标负责聚合、窗口和计算。

基础端点的必要补充单独列为实施前置：在既有模型/命令入口传递可选 providerId，并为 `ObjectOperations.properties().get(keys)` 提供有界的批量读取投影。沿用原来源授权、空值与错误语义；不新增 Provider 权限钩子，不做业务接口的并行包装。旧调用不带来源时保留原行为，歧义明确失败。

## 7. 保存什么，运行时得到什么

不保存样例数据、名称、组件代码或接口 URL。对象路径仍是 `VariableObjectSpec`，数据与操作仍分别保存 `PersistedDataBinding`、`PersistedOperationBinding`。

拟议 adapter 将稳定的对象类型、provider、成员类别和成员 ID 编成 capabilityId；ID 通过公共 factory 生成，业务不手拼字符串。对象路径放在原 binding 的 `config.object`，输入用原 query/input 的 `ValueBinding`，结果字段使用既有 `DataPath` 和 `OutputMapping`。不另造一种“对象表达式”。

```ts
// 结构示意：capabilityId 由拟议 adapter 根据真实目录生成。
const binding: PersistedDataBinding = {
  version: 1,
  source: {
    capabilityId: '<目录返回的稳定成员 ID>',
    version: 1,
    config: {
      object: {
        objectType: 'device',
        objectSource: { source: 'upper', upperKey: 'trigger.deviceId' }
      } satisfies VariableObjectSpec
    }
  },
  mapping: { fields: { value: { kind: 'path', path: ['value'] } } }
}
```

示例结果的 `value` 仅在输出 Schema 确实存在该字段时可选，不假设所有查询都叫 value。

- 动态起点由宿主明确绑定到它已有的变量/输出系统。预览必须另选样例，不把样例 ID 替换进正式配置。
- 关系解析沿用现有解析服务；VariableObjectSpec 到宿主变量的转换只保留一处，不在工作台、流程、指标各实现一次。缺失上游值时要求补充，不猜默认对象。
- 关系终点可能是集合。界面明确“一项/多项”，不取第一项、不默认均值；流程的遍历、通知策略和指标的聚合由各自宿主明确配置。
- 表现组件接收原类型数据和只读语义上下文；格式化文本不得成为指标计算的输入。单位转换必须是显式业务能力。
- binding version 代表适配契约版本，不虚构后端尚不存在的模型版本。执行前重读适用实例模型；结构变化时定位到失效字段，不静默选其他来源。
- 前端持久绑定不是后端可执行凭证。流程/指标服务需使用它们支持的明确解析适配，最终仍调用原来源能力；本轮设计不承诺浏览器运行时代替服务器执行。

## 8. 不同数据如何好看地展示和编辑

| 数据形态 | 默认表现 | 编辑 / 操作 |
| --- | --- | --- |
| 字符串、日期、枚举、布尔 | 紧凑键值；枚举 text 展示、value 提交；有语义状态映射才着色 | 显式 write 声明后就地输入；布尔值不默认用立即下发的开关 |
| 数值观测 | 值与单位相邻，下方弱化观测时间；质量和时间都来自声明 | 最新缓存、主动读取、属性下发三个意图分别命名 |
| 对象/数组 | 简短结构摘要，点开字段或有界列表 | 普通结构用类型编辑；业务约束较复杂才注册专用交互 |
| 文件/图片/位置 | 对应图标和预览；位置专用视图可按需注册 | 使用来源已有上传与位置编辑能力 |
| 时序数据 | 明确序列、时间、单位后才显示图表 | 历史窗口和查询由声明能力提供，不凭当前值生成曲线 |
| 业务记录 | 时间列表，紧凑摘要，必要时展开来源组件 | 事实本身只读；撤销/处理等作为来源动作另列 |
| 动作 | 动词名称 + 一句效果说明 + 就近执行入口 | 必填输入先出现，额外参数折叠；确认复用原 Operation 策略 |
| 关联对象/带属性关系 | 有方向的关系组、对象名称、关系实例属性摘要 | 统一维护入口；读取/编辑条件与正反向由来源声明 |

图标只辅助识别：数值、状态、时间、结构、列表、动作使用一致线性图标。保留文字，tooltip 解释数据类型、来源、单位与可用操作；不再用“可查询 5 项”代替具体内容。

设备物模型分两件事：“使用物模型描述的数据”和“修改物模型定义”。前者属于本方案；后者是设备/产品模块的模型管理业务，不能在通用属性编辑里偷偷修改类型、标识和协议定义。

设备写入目标值后，界面可显示“请求已受理，等待设备更新”；上报值继续保留原值和观测时间。业务对象 CRUD 成功后也应重读权威对象。动作没有返回效果证据时，不伪造“已生效”。

## 9. 视觉、状态与数据量

- 风格沿用 Ant Design 和 core 主题：`--primary-color`、`--primary-color-1`、`--text-color`、`--text-color-secondary`、`--jet-theme-bg-container`、`--jet-theme-border-secondary` 及 success/warning/error token；业务组件不写固定配色。
- 类型图标用中性色；主色表示当前选择和可操作入口；状态色只表达来源明确的状态。数字本身不因大就变红。
- 值、单位、时间组成稳定的对齐组；操作列预留空间，hover/focus 只改变可见性，不增减宽度。触屏和键盘同样可达，主要动作保持可见。
- 窄容器优先单列和就地展开，不挤出仅剩图标或省略到无法辨认的权限名称；弹层跟随宿主挂载边界，避免多层遮罩。
- 首次只读来源声明的默认观测及可见数据；能力发现不执行业务查询。长列表远程搜索和分页，图内继续保留默认 3 项预览，不自动遍历整条关系链。
- 区分尚未加载、加载中、空结果、未知值、拒绝、失败和过期。成功数据保留旧时间，新请求失败不把原值清零。
- 会话资源跟随对象、来源、参数和时间窗口释放。复用运行时已有完全相同请求共享；不引入全局用户数据缓存，不先实现新的批量调度器。

## 10. 三类消费者的可验证场景

| 场景 | 用户操作 | 应保存 / 应验证 |
| --- | --- | --- |
| 设备温度与压力 | 展示当前值，主动读一次，修改目标值 | 类型/单位/采样时间正确，受理不覆盖上报值 |

### 11.4 复杂度与职责约束

- 后端只有权威来源负责身份及业务授权；属性和动作在实际执行处使用原上下文。查询不额外读一次主体作为通用权限预检，生命周期清理不要求已删除对象还能被查询到。
- 实体注解只桥接权威对象身份，不从字段反射生成整套对象能力，不自动推断资产类型。暂不新增 CleanupProvider、删除编排器、权限门面或全局生命周期状态机。
- core 使用原 moduleRegistry、ObjectPresentation 和 data-capability；不再建 ObjectDataProvider、匹配规则引擎、全局结果缓存、请求调度器或每卡片轮询。
- 新公开接口只覆盖实际组件/宿主消费所需的契约；组件接收类型明确的数据与意图，API 留在 services/hooks。Vue/JSX 按 runtime-ui 约束控制在 300 行内，重复结构提取复用，组件层次不超过 5 层。
- 类型、作用域和来源歧义等边界约束集中处理；不重复检查已由 Schema、ORM 或来源保证的同一条件，不基于显示名/业务 ID 增加分支，不静默吞掉拒绝和执行故障。
- 个人配置不参与关注并集，不存观测快照/认证凭据/组件代码。缺失字段或暂时无权访问保留配置与明确状态，不当作对象删除。
- 主题色、图标、紧凑间距、加载/空/失败、键盘和 hover/focus 复用现有 Ant Design 与 core 风格；接口字段和 Provider 等内部概念不进入用户正文。

### 11.5 验证方式与完成口径

验证覆盖以下风险，并集中在对应阶段末执行：

- 契约：类型/实例模型差异、来源歧义、未知语义、原模型单位/枚举保留；旧 fields 与新 members 不双读。
- 语义：同端点不同关系事实不丢失，目标值与实测值不互换，部分/拒绝结果不生成否定结论，当前关系不伪装成历史归属；来源未声明推导或约束时不自行补齐。
- 生命周期：对象快速切换、组件卸载、来源卸载、慢请求与断流；旧结果不覆盖新上下文。
- 操作：配置时无副作用、取消草稿不提交、双击不重复派发、确认快照与目标一致；后台拒绝仍正确显示。幂等和最终授权由来源完成。
- 界面：数字/布尔/枚举/结构/集合、长名称、空值、拒绝和失败；窄屏、深色、主题色、键盘；hover/focus 不挤占空间。
- 个人页面：同对象多视图独立保存、另存为不覆盖原视图、默认引用与删除回退、切换前草稿处理；选择内容、拖动、调整尺寸、取消恢复、服务端失败保留草稿、刷新/再次打开、账号/租户/对象隔离；拖动不触发按钮，编辑不执行业务动作，缺失组件/字段不丢失原配置，窄屏不覆盖桌面坐标。跨设备恢复只有在视图存储服务实际验证后才计为通过。
- 对象删除：提交/回滚及无事务、真实批量结果、重复事件、集群实体回放不重复发、一个消费者失败后的重投、跨作用域同 type/id、不同用户的多视图与默认引用、两端托管关系及原同步链；补充来源卸载、解绑、离线不发对象删除，历史记录及关联对象保留；覆盖保存并发、迟到事件和同 ID 重建。现有事件的进程中断投递保证必须单独验证，不以普通单测成功代替。
- 组合：工作台展示、流程选择、指标字段引用对同一能力得到相同元数据及原值；服务端执行适配另设集成测试。
- 真实场景至少覆盖：同一设备的设备/规则两个能力来源；组织等已有非设备对象的普通字段和关系；一项已声明可修改的数据和一项真实动作；两个账号对同对象的多个视图；删除对象后配置/边清理而历史与关联对象保留。不为凑样例新增排班、工单或专用查询。

### 11.6 风险与范围外工作

实施前必须解决的风险：

3. **删除竞争**：保存与删除并发、迟到事件、同 ID 重建的语义由权威来源确认。若实际业务要求强一致或允许复用身份而现有契约不足，应报告具体分歧再补方案，不增加猜测式版本比较。
4. **兼容迁移**：旧 fields/detail/record 与新增能力消费不能双读；个人视图不能进入原模型发布/关注并集。只迁移本轮实际覆盖的调用。
