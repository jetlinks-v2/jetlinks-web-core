# 页面内容面板与页面头部插槽

## 1. 目标与当前结论

**项目布局的布局壳层统一给每个路由页面套 `ContentPanel`，默认开启，页面代码不需要自己包裹。**

三条规则：

1. **默认接管，但只在项目布局**：`CONTENT_PANEL_LAYOUT_VARIANTS = ['project']`，只有项目布局（`ProjectLayoutPage` → `BasicLayoutShell`）通过 `RouteContentSurface` 给路由内容套面板，此时 `DEFAULT_CONTENT_PANEL_ENABLED = true`。租户端复用同一个 `BasicLayoutShell`，但保持引入面板前的内容区结构；应用端 `ApplicationLayoutPage` 不经过 `RouteContentSurface`，是否包裹面板由该壳层自己决定。
2. **不做页面内容判断**：壳层**不去猜**页面里有没有 `ContentPanel`。壳层是跨路由常驻的，任何"按页面内容推断"的状态都会被带到下一个页面上去（见第 3.3 节的踩坑记录）。
3. **例外走代码侧声明**：不需要面板、或只需要布局不要背景与阴影的页面，由所属模块在自己的
   `index.ts` 里实现 `getContentPanelOverrides()` 声明（只在项目布局解析）。

> **不再使用路由 `meta.contentPanel`**（第 5 节记录了原因）：那份配置只能写在初始化菜单
> `baseMenu.json` 里，而菜单只在初始化流程推送到后端，导致**每改一个页面都要重新初始化菜单**，升级不友好。

页面里原有的 `ContentPanel` 由各模块**逐个删除替换**：删掉后页面自动获得布局面板，不会再出现双层卡片。

## 2. 影响范围与 owning module

- **owning**：`runtime-ui/jetlinks-web-core`
  - `src/types/content-panel.ts`（页面级面板声明类型：`ContentPanelConfig` / `ContentPanelOverride` / `ContentPanelOverrides`）
  - `src/types/module.ts`（模块扩展点 `getContentPanelOverrides`）
  - `src/layout/runtime/contentPanelOverrides.ts`（代码侧声明表：惰性收集 + 多别名匹配）
  - `src/layout/hooks/useRouteContentPanel.ts`（判定入口 + 默认开关，**不解析路由 meta**）
  - `src/layout/hooks/usePageChromeTarget.ts`（面板外头部容器）
  - `src/layout/components/RouteContentSurface/`（壳层内容区）
  - `src/components/ContentPanel/`、`src/components/PageChrome/`
  - `src/layout/shells/BasicLayoutShell.vue`、`src/layout/shells/BasicLayoutShell.less`、`src/layout/shells/ApplicationLayoutPage.vue`
- **消费方**：`runtime-ui/modules/*-ui` 的路由页面（约 200 个 `.vue`）
  - 没写 `ContentPanel` 的页面：**零改动**，在项目布局下直接获得统一面板
  - 写了 `ContentPanel` 的页面（约 98 个文件）：需要**逐页删除页内面板**，过渡期会短暂出现双层卡片
- **生效范围**：**只有项目布局**。租户端复用 `BasicLayoutShell`，但不挂 `--panel` 修饰类、不包裹面板；应用端 `ApplicationLayoutPage` 不经过 `RouteContentSurface`，保持自身结构
- **不涉及**：`ui/`（运营端）；外部 npm 包 `@jetlinks-web/components` 的 `j-page-container` 不动

现状统计（实测）：`j-page-container` 198 个文件、`FullPage` 144 个、`ContentPanel` 98 个，其中 `FullPage` + `ContentPanel` 同文件 64 个。

## 3. 契约

### 3.1 代码侧声明

模块在自己的 `index.ts` 里实现扩展点，返回本模块的页面清单：

```ts
// modules/authentication-manager-ui/index.ts
const getContentPanelOverrides = () => ({
  'project/Overview': false,          // 键 = 路由 name（即菜单 code）或路由 path
  'resources/Dashboard': false,
})

export default { /* 原有导出原样保留 */, getContentPanelOverrides }
```

类型（`src/types/content-panel.ts`）：

```ts
export interface ContentPanelConfig {
  enabled?: boolean    // false = 壳层不包裹面板，页面自绘背景
  padding?: number     // 覆盖 ContentPanel 内边距
  title?: string       // 面板标题
  background?: boolean // false = 保留面板留白/圆角，但背景透明、去模糊、去阴影
}
export type ContentPanelOverride = boolean | ContentPanelConfig
export type ContentPanelOverrides = Record<string, ContentPanelOverride>
```

**判定链**（`useRouteContentPanel`）：

```
是否项目布局？（CONTENT_PANEL_LAYOUT_VARIANTS = ['project']）
  ├─ 否 → { enabled: false }（不解析任何声明）
  └─ 是 → 查代码侧声明表（多别名匹配）
            ├─ 命中 → 用声明的值（false 等价于 { enabled: false }）
            └─ 未命中 → DEFAULT_CONTENT_PANEL_ENABLED = true
```

- **多别名匹配**：同一页面会依次用「路由 `name`、`route.path`、每条匹配记录的 `name` / `path` /
  `meta.componentCode`」去查表。菜单若配了 `routeName`，路由 `name` 就不等于菜单 `code`，
  多留别名可以避免"声明了却没生效"这种排查成本很高的问题。
- **只在项目布局解析**：非项目布局在 `useRouteContentPanel()` 处直接返回 `{ enabled: false }`，
  连显式声明也不会生效，保证面板不会逸出项目布局。
- 典型用法：
  - 全屏画布 / iframe / 需要自绘背景 → `false`
  - 只要布局对齐、不要白底和阴影 → `{ background: false }`
  - 需要统一面板但内边距不同 → `{ padding: 0 }`

### 3.2 壳层内容区结构

```
<section class="project-layout__route-content [--panel]">
  <div class="route-content-surface route-content-surface--panel">
    <div ref="chromeElement" class="route-content-surface__chrome"></div>   <!-- 面板外头部容器 -->
    <ContentPanel fill>                                                      <!-- 统一面板 -->
      <PageRouteView />
    </ContentPanel>
  </div>
</section>
```

声明为不包裹时退化为改造前的结构：`<div class="route-content-surface__chrome">` + `<PageRouteView />` 两个同级节点（空容器被 `:empty { display: none }` 隐藏）。

### 3.3 为什么不判断"页面里有没有 ContentPanel"（已踩过的坑）

第一版实现让页面里的 `ContentPanel` 上报"我自己有面板"，壳层面板据此让位（`display: contents`）。
`suppressed` 是壳层 setup 里创建的 `ref`，**壳层跨路由常驻**，所以：

> 从一个自带 `ContentPanel` 的页面跳到没有 `ContentPanel` 的页面后，`suppressed` 仍然是 `true`，
> 壳层面板一直停在 `content-panel--yielded` 上 —— 新页面拿不到背景和阴影。

DevTools 上能看到 `section.content-panel.content-panel--yielded.route-content-surface__panel`。

结论：**面板是否包裹只允许由代码侧声明决定**（模块的 `getContentPanelOverrides()`），
这是一个随代码发布、跟着路由走、无残留的状态。
任何"按当前页面内容推断"的壳层级状态都是跨路由泄漏源，不要再引入。

### 3.4 面板外页面头部

只有"头部必须落在页面板之外"的页面需要改代码：把那段内容放进 `PageChrome`。

```vue
<template>
  <!-- 页签/卡片切换充当面板顶栏：flush 让它与面板贴合 -->
  <PageChrome flush>
    <SlantedTabs :activeKey="activeType" :options="tabs" @change="changeType" />
  </PageChrome>

  <!-- 页内 Panel 删掉，内容直接写；面板由布局提供 -->
  <FullPage flex transparent-background>
    <EqualHeightColumns>...</EqualHeightColumns>
  </FullPage>
</template>
```

| 头部形态 | 写法 | 效果 |
| --- | --- | --- |
| 页签/卡片切换充当**面板顶栏** | `<PageChrome flush>` | 与面板连成一体（壳层闭合间距 + 面板左上角拉平） |
| 返回按钮、独立操作条 | `<PageChrome>` | 保留壳层默认间距；自身可再加 `margin-bottom` |

`flush` 用 `:has(> .route-content-surface__chrome > .page-chrome--flush)` 纯 CSS 判定，
不引入跨路由组件状态——这正是第 3.3 节踩过的坑要避免的东西。

- `PageChrome` 基于 `Teleport`，**保留页面自身的 provide/inject 与 scoped 样式**。
- 目标元素由 `RouteContentSurface` 通过 `provide` 下发元素引用（不是选择器：挂载期祖先还没连到
  `document`，`querySelector` 查不到）。页面在 `onMounted` 读取——壳层的模板 ref 走 post-render 队列。
- 拿不到目标时（BlankLayout / 全屏页 / 微应用宿主）`Teleport` 保持 `disabled`，内容原地渲染，不丢内容。
- 参考实现：
  - 贴合式 `modules/device-manager-ui/views/device/list/unified/index.vue`
  - 独立式 `modules/device-manager-ui/views/device/list/components/IotDeviceDetailView.vue`

### 3.5 fill 面板里的页面伸缩契约

面板接管时，页面根节点会成为 flex 项：

| 页面形态 | 页面根节点写法 |
| --- | --- |
| 自己算高度 / 用 `FullPage` 的整屏页面 | 保持不动（默认 `flex: 0 1 auto`，会收缩到面板高度） |
| 按内容高度排布、由面板滚动的页面 | `flex: 0 0 auto` |

不要依赖百分比高度：壳层链路是 flex 定高，百分比不可靠。

### 3.6 生效范围：只有项目布局

`RouteContentSurface` 被 `BasicLayoutShell` 共用，而 `BasicLayoutShell` 同时服务项目端（`ProjectLayoutPage`）
与租户端（`TenantLayoutPage`）。所以"是否包裹面板"不能只看页面声明，还要先看布局变体：

```ts
export const CONTENT_PANEL_LAYOUT_VARIANTS: readonly BasicLayoutVariant[] = ['project']

export const useRouteContentPanel = () => {
  const route = useRoute()
  const variant = useBasicLayoutVariant()

  return computed<ResolvedContentPanel>(() => {
    // 非项目布局：不解析任何声明，直接退化为改造前的内容区结构
    if (!isContentPanelLayout(variant.value)) {
      return { enabled: false, background: true }
    }
    return normalizeContentPanel(resolveContentPanelOverride(getContentPanelLookupKeys(route)))
  })
}
```

判定放在 hook 里而不是壳层里，是因为 `BasicLayoutShell`（决定 `--panel` 修饰类）与
`RouteContentSurface`（决定是否包裹）必须拿到同一个值；**壳层选择本身就由 `useBasicLayoutVariant()` 决定**
（`BasicLayoutPage.vue`），所以两者天然一致，不需要额外传参。

非项目布局下：

- `BasicLayoutShell` 不加 `.project-layout__content--panel` / `.project-layout__route-content--panel`，
  内容区回到改造前的块级布局；
- `RouteContentSurface` 走 `chrome 容器 + PageRouteView` 分支（空容器 `:empty { display: none }`）；
- 代码侧声明完全不参与解析。

应用端 `ApplicationLayoutPage` 不经过 `RouteContentSurface`，它的面板包裹由该壳层自己保留，不受本节影响。

## 5. 为什么放弃「路由 meta」方案（本轮变更原因）

第一版把开关做成路由 `meta.contentPanel`（#147），并写进模块的 `baseMenu.json`。问题在于：

```
baseMenu.json → handleMenu → 初始化流程 views/init-home 的 updateMenus
             → 后端 /menu/{owner}/_all → 运行时 POST /menu/user-own/tree → 生成路由 meta
```

菜单**只在初始化流程推送一次**，运行时读的是后端返回的菜单。所以：

- **每新增/调整一个不要面板的页面，都要重新初始化菜单**，升级不友好；
- 而且模块的路由表带不了 meta——路由 meta 的唯一来源是菜单项（`utils/menu.ts` 的
  `handleRoute` → `handleMeta`），`getAsyncRoutesMap` 只提供 component，所以也没法"就近声明"。

因此本轮把判定依据整体挪到代码侧：新增模块扩展点 `getContentPanelOverrides()`，
`RouteMeta.contentPanel` 与 `RouteContentPanelMeta` **已删除**，`baseMenu.json` 里的 7 处声明也一并清理。

本地验证例外效果：临时把 `DEFAULT_CONTENT_PANEL_ENABLED` 改成 `false`，或在注册表里改某个页面的值。
需要验证"非项目布局不包裹面板"时，把运行作用域切到租户端（`VITE_APP_RUNTIME_SCOPE=tenant`），
或临时把 `'tenant'` 加进 `CONTENT_PANEL_LAYOUT_VARIANTS` 再改回来。

## 6. 页面迁移清单与进度

### 6.1 迁移步骤

1. 删掉页面最外层的 `<ContentPanel>` / `<FullPage><ContentPanel>` 包裹，内容直接写。
2. 如果顶部有返回按钮、卡片切换、页签等**必须留在面板外**的内容，用 `PageChrome` 包起来；
   页签类"面板顶栏"用 `<PageChrome flush>`，返回按钮类用 `<PageChrome>`。
3. 整屏页面保留自己的高度机制（`FullPage` / 自算高度），不要改成依赖面板定高；
   作为布局面板的 flex 项时加 `flex: 0 1 auto; min-height: 0`，让它收缩到面板内容高度，
   页内滚动仍交给页面自己的滚动容器，避免第二条滚动条。
4. 页面确实需要"不要背景 / 不要阴影 / 不同内边距"时，由所属模块在 `getContentPanelOverrides()`
   里声明（见第 3.1 节），不要靠页内面板实现。

## 8. 风险与待确认点

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **壳层级状态跨路由泄漏（已发生）** | 壳层常驻，任何"按页面内容推断"的状态会带到下一个页面 | 包裹与否只由代码侧声明决定，无残留状态；已移除让位机制 |
| 过渡期双层卡片 | 页内面板还没删时，壳层面板 + 页内面板会叠加 | 按第 6 节逐页删除页内面板；这是计划内的临时状态 |
| `FullPage` 页面轻微双滚动 | 144 个页面用 `FullPage` 自算 `calc(100vh - top - padding)`，套进内部滚动面板后可能差几像素 | `FullPage` 会作为 flex 项收缩到面板高度；幅度小，需浏览器复核 |
| 页内面板 `height: 100%` 失效 | 壳层链路是 flex 定高，百分比高度不可靠 | 迁移时同时去掉页内面板；整屏页面保留自己的高度机制 |
| 声明键写错会静默失效 | 键是路由 `name`（菜单 code）或 path，写错不会有任何提示 | 多别名匹配（name / path / matched name / matched path / componentCode）+ 第 3.1 节写明键的取值 |
| `:empty` 依赖 | `.route-content-surface__chrome` 用 `:empty` 隐藏 | 目标节点保持纯空元素（模板里不写 `v-if` / 注释） |
| 租户端面板缺口（收窄后暴露） | 本仓库 `.env.development` / `.env.production` 都是 `VITE_APP_RUNTIME_SCOPE=project`，租户端当前不会被构建；一旦启用租户端，第 6.2 节已删除页内面板的 55 个页面会没有面板 | 启用租户端前需要重新评估：或把 `'tenant'` 加进 `CONTENT_PANEL_LAYOUT_VARIANTS`，或按页面补回面板 |
